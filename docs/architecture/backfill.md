# Backfill

`scooter backfill` runs an agent over history as it usually runs, from the first line or from a chosen point, without sending anything: to file a new skill's view from the messages before it was added, to file everything again from empty after the instructions changed, or to try a prompt or a skill against history with an agent of its own. It is a job, not a setting: the command writes the job's file into the agent's folder and exits, and the running runner takes the job at its next look, with no restart ([When the agent runs](runner.md#when-the-agent-runs)). Each of the job's batches is a run as a live one is ([A run, and the agent's folder](run.md)), which sends nothing. What makes history something to file again is that the datastore is the only source of truth ([Why it is built this way](../ARCHITECTURE.md#why-it-is-built-this-way)). The README gives the owner's procedures ([Backfills](../../README.md#backfills)).

## Files

- `src/runner/enqueue.mjs`: `scooter backfill`: its arguments, checked against `agents.yaml` and the datastore, and the job's file it writes.
- `src/runner/backfill.mjs`: the runner's side of a job: taking it, its start, its batches and its lane, its message, and cancelling it.
- `src/runner/replay.mjs`: replayed batches: one of the owner's days each, `$now$` the batch's own time, the prompt, and the job's sessions.
- `src/common/jobfile.mjs`: the job's file: its format, its check, its reader, and the list of the jobs' files, for the command, the runner and `scooter status`.

## The command

```text
scooter backfill <agent> [--from <UTC date or seq>] [--skills <names>] [--writes <paths>] [--empty] [--hold-live] [--prompt <file>]
scooter backfill --agent-file <file> [--from <UTC date or seq>]
```

It runs as the runner's user, natively as `sudo -u scooter-runner scooter backfill …`, and in Docker as `docker compose run --rm runner backfill …`. Where `scooter-runner` is a user of the machine, it refuses to run as another, root above all, before it reads or makes anything: it writes nothing, exits with 2, and says how to run it, as `doctor` does ([doctor](install.md#doctor)). Without that user, as in development, it runs as whoever runs it. *Why:* run as root, as `sudo scooter backfill`, the form the README gives the bridge's commands, it would say the job was queued and leave the jobs' folder, and for a new agent's folder that folder too, as root's, mode 0700: the runner can't read it, so it passes it over and the job never runs; a later command as the runner's user can't write there; and lifelog's folder made so stops the runner at its start. It would also be root writing in a folder the runner's user controls ([Folders other users control](../ARCHITECTURE.md#folders-other-users-control)). `src/cli.mjs` asks who runs it before it reads the runner's settings ([The CLI](configuration.md#the-cli)). *Why first:* natively `runner.env` is the runner's user's alone, mode 0600 ([setup](install.md#setup)), so another user, root apart, can't read it, and would be told that, and that `OPENROUTER_API_KEY` is required, and not how to run the command; and root's refusal would come only after `runner.env` was read. It reads `runner.env`, `agents.yaml` as the runner does ([agents.yaml](configuration.md#agentsyaml)), and the datastore, checks its arguments against them, writes the job's file ([The job's file](#the-jobs-file)), says where, and exits. It takes no lock and holds no socket: it runs beside a running runner, and with the runner stopped, whose next start takes the job. `--skills` and `--writes` each take one value or more, up to the next flag; the others, one or none. Every fault is reported at once, each on a line of its own, as `agents.yaml`'s are, within each of four steps, each taken only once the one before has passed: the command line; the agent, an agent of `agents.yaml` by its name, or the file of `--agent-file`, read and checked; the agent's trigger for new messages, `--skills`, `--writes` and `--prompt`, a file of `--prompt` that can't be read stopping this step alone; and `--from`, which needs the datastore. *Why steps:* each needs what the one before gives: the agent for its skills and writes, the job's writes for its prompt, and arguments that hold before the datastore is read. Given no argument, it prints its two usages. Exit codes: 0 once the job is written; 2 for a call or a configuration it can't take, such as a flag it doesn't have, an agent `agents.yaml` doesn't have, or a fault of `agents.yaml`, and for another user than the runner's; 1 when it fails otherwise, as on a datastore it can't read.

- **An agent of `agents.yaml`**, by its name, can be run with fewer skills and narrower writes. It must have a trigger `on: new-messages`, as an agent given in a file must: a job's runs are given the lines of its channels, so a job of an agent without one would be given none, and `--empty` would still empty what it names; the command refuses it, and so does the runner, taking a job whose agent has lost its trigger since ([Taking a job](#taking-a-job)). `--skills` names some of its skills, by their folders' names, and its runs are given those alone, after the runner's own ([show, and the runner's skill](agent.md#show-and-the-runners-skill)); without it, all of the agent's. `--writes` names paths of the data folder, of the form of `writes`, each in the agent's own `writes`, the same file or in a folder it names, and the sandbox holds the job's runs to them as it holds any run to its `writes` ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)); without it, the agent's own. A path that isn't in the agent's `writes` is refused, naming it by its place, `--writes 2`. *Why:* issue 25: an agent of `agents.yaml` can be run with fewer skills and narrower writes, which the sandbox enforces.
- **`--prompt <file>`** gives the job's runs the text of the file as their message, in place of the prompt of the agent's trigger for new messages, with the same variables ([The prompt](runner.md#the-prompt)). The command reads the file when it is run, as UTF-8, a byte-order mark at its start left out, and keeps the text in the job's file, so the job keeps it across restarts, and a file changed or removed afterwards changes nothing. It is checked as a trigger's prompt in `agents.yaml` is, with `$run.writes$` the job's writes, and a faulty one is refused, naming the fault: blank, a variable the runner doesn't know, U+0000, half of a surrogate pair, a first `@`, or longer than `PROMPT_MAX_BYTES` once filled in with the longest values its variables can take. A file that isn't a file, isn't UTF-8 or is larger than `PROMPT_MAX_BYTES` is refused before. The agent's own prompt, the file that pi appends to its system prompt, such as `prompts/lifelog.md`, is the agent's, and the command can't change it, so history is filed under the rules live runs have. Without `--prompt`, the job's runs get the trigger's prompt, and the command holds it to the job's writes, which may make `$run.writes$` longer than the agent's own. *Why:* a backfill can give an existing agent another prompt for its runs, the message the trigger would give them, while the agent's own system prompt stays its own; an agent given in a file couldn't serve for that, since it can't write into another agent's folder; and a run narrowed to one view is otherwise told only what it may change, and not that it files for that view alone. This replaces, for the agent's own prompt only, issue 25's sentence that the command sets the scope and not the prompt. A comment on the issue records it ([issue 25](https://github.com/Janmajayamall/scooter/issues/25#issuecomment-7099032910)).
- **`--agent-file <file>`** gives an agent of its own, the way to try a prompt or a skill against history without touching an agent of `agents.yaml`. The file is one agent in the format of `agents.yaml` ([agents.yaml](configuration.md#agentsyaml)), `agents:` and the agent by its name, checked as `agents.yaml` is, its faults named by the file's lines, and besides: its name is no agent's of `agents.yaml`; each path of its `writes` lies in its own folder, `agents/<name>/`, which the runner makes; its `sends` is `[]`; and it has a trigger `on: new-messages`, whose prompt its runs are given and whose `channels` say which lines are their work. Its paths of the config folder, `prompt` and `skills`, are relative to the config folder, as `agents.yaml`'s are. The command reads the file when it is run, at most `JOB_AGENT_FILE_MAX_BYTES`, and keeps its text in the job's file. It takes `--from` and no other flag: `--prompt` among them is refused, as the file brings its own prompts. Its scheduled triggers, if it has any, never run: a job runs batches of messages. Its folder stays when the job is over, in the backups too, and a later job under the same name goes on in it, with the views, the memory and the history the earlier one left ([Taking a job](#taking-a-job)); to try again from empty, the owner gives the agent another name, or removes its folder, while no job of it is there. *Why it stays:* the folder is what the job made, for the owner to compare, and nothing tells the runner when the owner is done with it. *Why `sends: []`:* issue 25 has such an agent send nothing, and a job's runs send nothing anyway, so a file that named a channel would say what doesn't happen. *Why the config folder:* the runner copies the prompt and the skills for each run from the config folder, which its user can read, as it does for the agents of `agents.yaml`, and the format is then that of `agents.yaml`, paths and all. *Cost:* to try a prompt the owner puts it in the config folder.
- **`--from`** is a UTC date, the day folder a line was stored in, such as `2026-11-09`, or a `seq`, such as `812`. A date is the first line stored that day, or, when none was, the first stored after it; a date with no line on or after it, and a `seq` past the newest line, are refused, naming the newest. Without it, the job starts at the first line. The command turns a date into its `seq`, and the job keeps that. *Why not a time:* a line's `at` is when it was sent, out of order for messages caught up late, while the day folders are in the order the lines were stored. *Why refuse a `seq` past the newest:* such a job would have nothing of history to give, and live runs give what comes after.
- **`--empty`** clears what the job's `writes` name in the agent's folder, and commits that, before the first batch ([The start](#the-start)). *Why a flag:* the owner can't empty the folders by hand, since the runner puts them back from the last commit at every start.
- **`--hold-live`** makes live runs wait until the job has finished, and the job replay in order ([When a job runs](#when-a-job-runs)).

## The job's file

`agents/<agent>/jobs/<id>.json`, in the folder of the agent it runs, mode 0600, in a folder of mode 0700, which the command makes, the agent's folder too when it is new. Its format is `src/common/jobfile.mjs`'s:

```json
{
  "id": "20261123T101500123-0001",
  "agent": "lifelog",
  "written": "2026-11-23T10:15:00Z",
  "from": 812,
  "skills": ["books"],
  "writes": ["agents/lifelog/views/books.csv"],
  "empty": false,
  "holdLive": false,
  "prompt": null,
  "agentFile": null,
  "progress": {"started": "2026-11-23T10:15:03Z", "until": 1890, "cursor": 1203, "given": 391,
               "retry": [{"seq": 1201, "attempts": 1, "due": "2026-11-23T11:02:00Z", "reason": "not marked"}],
               "skipped": [1031], "wait": null}
}
```

- `id` is an ID as `createIds` makes them ([Atomic files and hand-offs](shared-code.md#atomic-files-and-hand-offs)), the UTC time to the millisecond and a counter, so the names sort in the order the jobs were written; the file is named by it, and it names the job in its sessions, its commits, its tag, its message and `scooter status`.
- `skills` and `writes` are null for the agent's own; `prompt` null for the prompt of the agent's trigger for new messages; `agentFile` null for an agent of `agents.yaml`, and otherwise the file's text, with `skills`, `writes` and `prompt` null and `empty` and `holdLive` false.
- `progress` is null until the job has started, and then its lane, as the state's own is for live runs ([State](runner.md#state)): when it started, `until`, where it stops, its `cursor`, how many lines it has given, `retry` and `skipped`, what it gave up on; and `wait`, null unless a setup error or an outage holds back the job of an agent given in a file, and then `{ since, cause, reason, next, tries }`, as the state's `paused` is: since when, `setup` or `outage`, why, the next try, and the failed tries in a row ([Its batches](#its-batches)). It is always null for an agent of `agents.yaml`.
- **Written whole, under a name no other file has.** The command writes it under a temporary name beside it, syncs it, and links it to its own name, which fails when the name is taken, as by a command run in the same millisecond, and the job then takes the next ID (`writeNewFile`). So a runner reads the whole file or none, and two commands never write over each other.
- **Read with care, by whoever reads it:** without following a link, without waiting on a FIFO, only if it is a regular file with one name, and up to `JOB_FILE_MAX_BYTES`. *Why so careful:* the runner's user writes it, and `scooter status` reads it as root ([Folders other users control](../ARCHITECTURE.md#folders-other-users-control)), and nothing in the jobs' folder may stop the runner, or have root read another file.
- **Then checked for what the runner needs, and nothing else** (`checkJob`, `readJob`). Each field above is needed, of its form: the progress of a job that has started, each field of a retry and `wait` among them. One missing or of another form refuses the job, with a fault that names the field, and the job doesn't start, or doesn't go on. Its `id` must be its file's name, and its `agent` its folder's. A job of an agent given in a file that also has `skills`, `writes` or `prompt`, or `empty` or `holdLive` true, is refused, since it would not do what its file says. A field the runner doesn't know, at the top, in `progress`, in `wait` or in a retry, is ignored, by the runner and by `scooter status`, and the runner's saves keep those at the top and in `progress`. *Why:* what keeps a file from stopping the runner is the care in reading it and the check of what the runner uses, and a field nothing uses can't mislead it; so a file may hold more than this version reads, while a job without what it needs is refused before it starts. This replaces the strict reading the plan of the agent model asked for, as the state's is ([State](runner.md#state)).
- **The runner alone changes it** after the command has written it: atomically, after each batch. The command never changes one it wrote. `jobs/` is the runner's in the agent's folder: `writes` can't name it, the agent's own runs never see it, and git ignores it ([agents.yaml](configuration.md#agentsyaml), [What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)).

## How the runner runs a job

### Taking a job

At each round the runner looks at the jobs' folders of the agents' folders (`listJobFiles`): `agents/<name>/jobs/` for every name in `agents/` that an agent can have, while each is a folder, not a link, that the runner can read: any other holds no job, so no folder the runner's user makes there can stop the runner. It holds one job at a time, of whichever agent: a job that has started before one that hasn't, and the oldest first among each, by its ID. It takes the next only once the one it holds is over, finished or cancelled; a job that waits after a failure of its own ([Its batches](#its-batches)) is still the one it holds, so the jobs after it wait with it. *Why one at a time, whatever the agent:* runs never overlap anyway ([The loop](runner.md#the-loop)), and one queue keeps the order the jobs were written in. *Cost:* a job of one agent waits for a job of another to finish. *Why one that has started first:* it has tagged the agent's folder, and maybe emptied it, and with `--hold-live` it holds live runs back until it has finished, after a restart too; an older job that the runner refused, as for a prompt not in the config folder, and can take after a restart once the config is put right, must not come in between, which would let live runs file into views half filed from empty. *Cost:* two jobs that have both started, which only a started job refused at a start and taken again later makes, go by their age, not by which ran last.

Taking it, the runner reads the file (`readJob`), and checks the job against the config as it is now, as the command checked it then: the agent is the runner's, of `agents.yaml`, or, for an agent given in a file, the file's text is one ([The command](#the-command)); it has a trigger for new messages; its skills are the agent's; its writes lie in the agent's; and its prompt, or each prompt of the agent's triggers for new messages, passes the checks of a prompt with the job's writes. A file that isn't a job's, or a job that can't run as the config is now, such as one whose skill has since left `agents.yaml`, is refused, logged as `runner.job_refused` with the reason, and passed over: the runner goes on with the next. It is read and checked again at every look while the runner holds no job, so a job refused for the config is taken once the config is put right, and logged once while the file stays as it is, by its inode, its size and its change time, whatever the reason then. Nothing but the log says so: `scooter status`, which reads no config, shows such a job as waiting to start ([scooter status](bridge.md#scooter-status)). A name in `jobs/` that isn't `<id>.json` is no job, and is refused so; names that start with a dot, such as the command's temporary files, are passed over.

For an agent given in a file, taking the job readies its folder as a start readies the agent's ([Starting up](runner.md#starting-up)): made if it is new, with its repository and its first commit, git's leftover locks removed, and what a run cut short left thrown away ([The clean-up](run.md#the-clean-up)); a folder already there, which an earlier job of that name left, is kept as it is, with its views, its memory and its history. Its repository keeps what its `writes` names, as any agent's does ([The agent's folder](run.md#the-agents-folder)).

### When a job runs

- **Without `--hold-live`**, a step of the job, its start or a batch, runs only when nothing live is waiting: no work items to give after the live cursor, quiet or not, no due retries, and no scheduled task ([When the agent runs](runner.md#when-the-agent-runs)). Runs never overlap, so a message that arrives during a batch of the job waits for it, and then goes first. While its own lines wait to be tried again, the job takes the lines after them, as live runs do.
- **With `--hold-live`**, the job comes before live runs: from the moment the runner takes it until it has finished, no batch of messages and no scheduled task runs, across restarts, since the job's file is there, and across pauses, which hold the job as every run. And the job replays in order: while a line waits to be tried again, it takes nothing, also when another is due, and waits until it is due, as live runs wait for it. *Why:* issue 25 has a job that holds live runs back replay in order, so that a rule the owner sent in a message that needed a second try is learned before the days after it are filed; the plan of the agent model hangs the rule on the flag, not on what `writes` names, since the runner doesn't know what memory is. *Cost:* messages that arrive meanwhile get no reply until the job is over. A scheduled task that comes due during the job runs once it has finished, unless the runner starts again meanwhile, whose start counts it as dealt with, as it does any task already past ([When the agent runs](runner.md#when-the-agent-runs)).
- A pause, after a setup error or an outage, holds every run, the job's among them, until the next try ([Failures](run.md#failures)). A job of an agent given in a file that waits after a setup error or an outage of its own gives no batch until its own next try, and holds back no live run or scheduled task, only the jobs queued behind it, since the runner holds one job at a time ([Its batches](#its-batches), [Taking a job](#taking-a-job)).

### The start

The job's first step, holding `run.lock` and giving way to `backup.lock` as a run does ([The locks](exchange.md#the-locks)), since it changes the agent's files and `.git`:

1. **The tag.** The agent's last commit is tagged `before-backfill-<id>`, an annotated tag whose message says what the job was asked: when it was written, `--from`, its skills, its writes, `--empty` and `--hold-live`, and the prompt its runs are given, before its variables are filled in: the text of `--prompt`, or that it is the trigger's; for an agent given in a file, the file's text. The message is kept as it is given, every line of it, one that starts with `#` among them (`--cleanup=verbatim`, `git: an annotated tag…` in `test/tools/git.test.mjs`): `git cat-file tag before-backfill-<id>` shows it. A tag already there, which only a start of the same job cut short makes, is left where it is. *Why the prompt with the tag:* a job's sessions go when it is over, and the prompt would go with them, where the tag stays, beside the commits the job made, so the difference the job made and what it was told are kept together. *Why the tag:* issue 25: the way back, and the difference the job made, are there.
2. **`--empty`**: what the job's `writes` names in the agent's folder is emptied, a folder of what it holds and a file removed, an entry whose way is blocked passed over and nothing read through it ([A change of writes](run.md#a-change-of-writes)), and that is committed, `lifelog: backfill <id>, from empty`. A path of the job's `writes` outside the agent's folder is left as it is: the runner never reads there ([agents.yaml](configuration.md#agentsyaml)).
3. **Where it stops,** `until`: the agent's position, its live cursor, for an agent of `agents.yaml`; the newest line, for an agent given in a file. Then the job's progress is saved, its cursor before `from`.

*What a stop or a crash between them costs:* the start is done again at the next look, as one that never was. The tag stays where it was, before anything the job changed. Emptying again changes nothing the job needs kept: the views are empty, and what live runs filed there meanwhile, without `--hold-live`, is of lines up to the new `until`, which is taken again, so the job files them again. A full disk at the save stops the runner, as one at the state's does, and the next start does the start again.

### Its batches

The job's lane is drawn from as the live lane is ([The batch](runner.md#the-batch)), and replayed:

- **A batch is of one of the owner's days.** Due retries first, then work items after the lane's cursor, at most `BATCH_MAX_ITEMS`, up to `until`. Every item it takes was sent on the local date, in `SCOOTER_TZ`, of the first item's `at`, and it stops at the first sent on another date. So a message caught up late, whose `at` is on an earlier day than those around it, is a batch of its own. A message that an edit in the batch brings in, from the lane's retries or from what it gave up on, joins whatever its day, as it may take a batch past `BATCH_MAX_ITEMS`. The work items are those of the channels the job's agent's triggers for new messages name. *Why the local date, and not the session's day:* every item a batch takes was then sent "today" by its `$now$`; with the session's day, a message at 00:10 would share a batch with one at 23:50, and one of the two would be read against the other's date. *Cost:* a message sent just after midnight is in the next day's session, where a live run would have had it in the day before's until `SESSION_ROLLOVER_HOUR`; a session is the agent's conversation, not where anything is filed.
- **`$now$`** is the time of the batch's newest item, the latest `at` among them, not the current time, so "today" and "yesterday" in old messages mean what they meant then, and `$now$` is never before an item's time. The runner's skill tells the agent to count "today" from the time the run's message gives ([show, and the runner's skill](agent.md#show-and-the-runners-skill)).
- **The prompt** is the job's own, `--prompt`, or that of a live batch: the first trigger `on: new-messages` of the job's agent that names the channel of one of its lines ([The prompt](runner.md#the-prompt)); with `$run.writes$` what the job may change, as the VM has it, such as `/data/agents/lifelog/views/books.csv`. pi's system prompt is the agent's own, as for live runs, so the rules it reads from its memory, the owner's current preferences among them, apply to all of history, unless the job empties the memory ([Memory](#memory)).
- **A message deleted later in history is never given,** as a live batch never gives a message already deleted: the runner's index says it is deleted, and only its deletion is given, on its own day. A message is given as it was sent, and its later edits each on its own day. *Why:* an index as of each batch's time would be a second one to keep, and the views come out the same: the agent files the message's text, and changes it when its edit comes; a message deleted since is never filed, and its deletion finds nothing filed. *Cost:* a replayed batch can be given a deletion whose message, of an earlier day, it was never given.
- **What it may change:** the job's `writes`, and nothing else: the runner gives the sandbox the job's `writes` in place of the agent's for each batch, and the VM sees the agent's `reads` and `writes` as it always does ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)). A write anywhere else, the agent's memory among them when the job's `writes` leave it out, fails in the VM with "Read-only file system", and the batch goes on. The check, the commit and the clean-up after a batch are a live run's.
- **Sessions:** each of the owner's days gets its own, `<agent>-backfill-<id>-<day>`; with `session: none`, none. They go when the job is over: only names of that form, of that job. *Why:* they serve the job alone, no live run uses them, and a job over a year makes about 365, up to `SESSION_MAX_BYTES` each, in a folder that is backed up.
- **Silent:** what the agent queued with `send` is dropped, it gets no reactions, and its failures send no notice ([What send and mark leave](run.md#what-send-and-mark-leave)), but for the runner's own when a job of an agent given in a file starts to wait (below).
- **Its outcome** settles the job's lane as a live batch's settles the live lane (`settleLane`, [Failures](run.md#failures)), with `skipped` in the place of `failed`, from which an edit in a later batch of the job brings a message back as from `failed`, and a deletion settles it ([The batch](runner.md#the-batch)); `given` counts each line given for the first time. For an agent of `agents.yaml`, a setup error or an outage pauses every run, as after a live run, without a notice, and a batch that gets through ends a pause: the job runs with the agent's own model, so a live run would meet the same failure, and send its notice. A batch leaves `lastRun` alone, which is the live runs', so a live failure after one is still the first of its row and sends its notice.
- **A job of an agent given in a file waits on its own.** That agent has a model of its own, which can fail where the runner's agent's doesn't, as one the key's guardrail doesn't allow. So a setup error or an outage in one of its batches leaves the pause of every run as it is, and holds back that job alone: its progress gets a `wait`, as the state gets `paused`, with since when, the cause, the reason, the next try and the tries in a row, the next try as far off as a pause's ([Failures](run.md#failures)), and its lines wait in its retries with their attempts unchanged. The runner gives the job no batch before that try, while live runs and scheduled tasks go on as usual. A batch that gets through, or fails on its own, which means OpenRouter answered, ends the wait. The wait is in the job's file, and a start leaves it as it is, where it brings a pause's next try forward. When the wait starts, at the first such failure after a batch that got through or none, the runner sends the owner one notice of its own, as it does at a live run's first failure, naming the job: `⚠️ Backfill 20261123T101500123-0001 of lifelog-try couldn't run a batch (OpenRouter answered 403). It waits until this is fixed, and tries again every 30 minutes; your messages are handled as usual meanwhile, and later backfills wait for it. Remove its file to cancel it.` The tries after it send nothing. The job's agent still sends nothing. `scooter status` shows the job as waiting, since when, why and the next try ([scooter status](bridge.md#scooter-status)). The job never gives up by itself, as a pause doesn't, and the jobs queued behind it wait for it, since the runner holds one job at a time ([Taking a job](#taking-a-job)), until it gets through or its file is removed ([Cancelling](#cancelling)). *Why:* such a job's failing model would otherwise pause lifelog's runs at every try, so that a new message waited for the pause, up to 30 minutes, and the owner was told nothing; so a failing job of an agent given in a file waits on its own. A job of an agent of `agents.yaml` keeps the pause of every run, as the plan of the agent model has it. *Why the notice at the start of the wait:* it is what the owner has to act on, and a failure of pi's own in a job's batch counts an attempt and ends in the job's message, as before. *Why a start doesn't bring the try forward:* the runner starts again after an error ([Restarts](runner.md#restarts)), and the job isn't urgent; its tries stay as far apart as they were. *Cost:* once the cause is fixed, the job goes on at its next try, up to 30 minutes later, a restart notwithstanding; and the notice is a second one if the runner stops between writing it and saving the job's file.
- **Commits:** `lifelog: backfill <id> #812-#831`, the lowest and the highest `seq` of the batch, each batch as it passes, as live runs commit ([After a successful run](run.md#after-a-successful-run)).
- **Its lane is its own:** the job neither reads nor changes the live lane, `cursor`, `retry` and `failed` of `state.json`. *Cost:* a line that waits in the live retries when the job starts lies in the job's range, and is given by the job and again by the live runs; lifelog's prompt has the agent look for a row of the same `source` before it adds one. *Why not take it out of either:* each lane settles a line by its own marks, and the runner settles no line because of another ([The batch](runner.md#the-batch)).
- **Saved:** the notice of a wait that starts, if any; the job's progress, in its file; then the state, with the pause. *What a crash between the commit and the save costs:* the batch is given again, as for live runs, and a wait's notice may go out a second time. *Between the two saves:* the pause the batch started or ended, which a start tries again at once; a batch of an agent given in a file changes nothing in the state.

### Memory

What the job does to the memory is the owner's choice, by what `--writes` names. Left out of the job's writes, the memory can't change, and the job files history under the rules of today: the agent reads the memory, the owner's preferences among them, before each batch. With `--empty` and `memory/` among the job's writes, which the agent's own `writes` name in the default `agents.yaml`, the memory starts empty, and the rules the owner sent as messages are learned again in the order they were sent; `--hold-live` then has them learned before the days after them are filed. Rules in the config folder apply to all of history either way. *Why so:* issue 25.

### Finishing

When the job's cursor has reached `until`, and no line of its retries waits to be tried again, the runner sends one text, `by: "runner"`, to `DEFAULT_CHANNEL`, also with `sends: []`, as notices go ([Notices](run.md#notices)): `Backfill 20261123T101500123-0001 of lifelog finished: it was given 143 lines, and gave up on #1031 and #1207.` It counts no rows: the runner doesn't read the views. Then the job's file goes, and its sessions. A line of its retries that no batch would give, a message deleted since it was given, holds it back no more. The tag and the job's commits stay. *Why the text before the file:* a crash between the two sends it twice and never loses it.

### Cancelling

A job is cancelled by removing its file. At its next look the runner drops what it holds of the job and removes its sessions, and logs `runner.job_cancelled`. A file removed during a batch is noticed when the batch is saved: the batch is recorded, its commit kept, and the file isn't made again. The sessions of a job whose file went while the runner was stopped go at its next start, for every agent's folder (`sweepJobSessions`). The tag and the job's commits stay: `git reset --hard before-backfill-<id>` in the agent's folder, with the runner stopped, goes back to before the job ([Backfills](../../README.md#backfills)). It also takes away what live runs committed since the job started, which without `--hold-live` they do between its batches: what they filed from messages that arrived meanwhile, and what scheduled tasks changed. The state still has those messages as handled, so they aren't given again: the owner sends them again, or runs a backfill `--from` the first of them. *Cost:* a file removed in the instant between the runner's look at it and its write is written again, and the job goes on: removing it again cancels it.

### What else can be in its place

- **A file rewritten while the runner holds the job**, which only a hand can do, is written over at the next save with the runner's own record, and that is logged, `runner.job_rewritten`. *Why:* the runner alone counts what the job has given, so each line of the job's range is given once; a file another wrote, with another cursor, would give lines twice, or never. A file rewritten while the runner is stopped is read at its next start, and checked as any is ([The job's file](#the-jobs-file)).
- **Something other than a file in its place,** such as a folder, drops the job at the next save, as a removal does, and is left as it is, logged as `runner.job_replaced`; it is refused, and passed over, from then on.
- **A job's file larger than `JOB_FILE_MAX_BYTES`** is refused when it is read. The runner never writes one: only a job that gave up on about a million lines comes near it, and then the save fails, which stops the runner.
