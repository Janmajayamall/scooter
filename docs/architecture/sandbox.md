# The sandbox and the VM image

Every run of pi gets a fresh Gondolin micro-VM on QEMU, booted from an image Scooter builds. The sandbox is what the runner runs pi through: one small interface, a VM for each run that sees and may change what the run asks for, with its environment, the accelerator, and the limits on what a run may take from the runner. Its network is [the network policy](network-policy.md). The image, and `scooter build-image`, which builds it, are here too. What pi can reach, and the users the VM and QEMU run as, are in [The boundaries](../ARCHITECTURE.md#the-boundaries).

## Files

- `src/runner/sandbox/index.mjs`: the sandbox interface, the check of a run's spec (`checkRunSpec`), `SandboxSetupError`, and `createOutput`, the output both sandboxes keep.
- `src/runner/sandbox/gondolin.mjs`: the real sandbox, `openGondolinSandbox`: the runner's home and temporary folder, the image and the accelerator checked as it opens, one VM per run, and the limits on what a run may take; and `bootCheck`, for `doctor`.
- `src/runner/sandbox/view.mjs`: what a run's VM sees of the host and may change, as Gondolin's providers: `viewProvider`.
- `src/runner/sandbox/accel.mjs`: `AGENT_ACCEL`, by opening `/dev/kvm`.
- `src/runner/sandbox/image.mjs`: the build file and its pin of pi, the image's `scooter-image.json` and the check of it, `packages.txt`, and `scooter build-image`.
- `config/image/build.json`: what is in the image, with Alpine's release and pi's version pinned.

## Settings

| Variable | Default | Meaning |
|---|---|---|
| `AGENT_ACCEL` | `auto` | How pi's VMs run: `auto`, `kvm` or `emulation`; `hvf` is kept for macOS ([Acceleration](#acceleration)) |

`build-image` reads only `DATA_DIR` and `CONFIG_DIR`, from `runner.env` or the environment, checked as the runner's settings are ([build-image](#build-image)).

## The sandbox interface

`src/runner/sandbox/index.mjs` says what a sandbox is: `{ accel, imageBuiltAt, run(spec, { signal }) }`, opened by the runner at its start ([Starting up](runner.md#starting-up)). A spec is `{ argv, cwd, env, files, timeoutMs, policy }`, which the runner builds for each run ([A run](run.md#a-run)):

- `argv` starts with the program's name, `pi`; no shell reads it. Where the image keeps pi is the sandbox's business.
- `files` is `{ root, reads, writes, hide }`, absolute paths on the host, which the VM sees at the same paths: of the folder `root` the VM sees what `reads` and `writes` name, each a file or a folder with all it holds, and the folders that lead there; it may change only what `writes` names, each `{ path, folder }`, a folder with all it holds or a file; and it never sees what `hide` names ([What a run sees and may change](#what-a-run-sees-and-may-change)).
- `env` is the program's whole environment but the secrets.
- `policy` is `{ model, internet, zdr, secrets }`. `secrets` maps `OPENROUTER_API_KEY` to the key and the hosts it may go to, and the sandbox sets the variable to a placeholder ([The key](network-policy.md#the-key)).
- `run` resolves with `{ code, signal, stdout, stderr, timedOut, stdoutCut, wroteTooMuch }`, `code` being null when the program didn't exit by itself: a timeout, an abort, a run past what it may write, or a VM that was lost. It rejects only when the program couldn't be run at all, such as when the VM doesn't start. `signal` aborts the run, as a timeout does.

`checkRunSpec` refuses a spec whose `env` sets a secret's variable; a path of `files` that isn't absolute and cleaned, as `path.posix.normalize` leaves it, or isn't inside `root`; and a path of `writes` that lies in a path of `hide` or holds one, since through it the VM could make the hidden path, or see it. Both sandboxes check every spec this way.

**The fake sandbox**, for the tests (`test/support/fake-sandbox.mjs`), makes a folder for each run that stands for the VM's root and puts each path `files` shows at its path there: a link to the host's file or folder, or, for a folder that holds a hidden path, a folder of links to everything but that, so `sessions/` isn't there at all, as in the VM. It doesn't keep the stub from changing what `writes` doesn't name: it gives the stub the run's `writes` (`PI_STUB_WRITES`), and the stub writes only there, as the VM would let it, and notes each write it leaves out in `refused.txt` in its control folder; the sandbox tests and `test/tools/vm.test.mjs` show the real sandbox holding pi to them. It runs `test/support/pi-stub.mjs` with Node, through `proc.run` and the test's clock, with the spec's environment, a placeholder for each secret, and `PI_STUB_*` variables of its own, which the stub leaves out of what it records. The stub takes pi's command line, finds each path it is given inside that folder, keeps its session as pi 1.5.2 does, writes OpenRouter's answers to the network log in its format, and prints its answer or fails as pi does. It acts on keywords in each item, such as `IGNORE`, `FAIL`, `ASK` and `SAY`, and on keywords anywhere in the batch, such as `OPENROUTER=<status>`, `CRASH` or `SYMLINK`, which a test can also set in `behavior.json`, in the stub's control folder, `words` among them: a failure that must stop so that the next try succeeds, such as a key being fixed, can't come from the message, which the next try shows again.

## A VM for each run

`openGondolinSandbox` is the runner's sandbox. Each `run(spec)` makes a VM from `runner/image/` with the spec's `files` mounted, boots it within `VM_START_TIMEOUT`, or the run's own time when that is shorter, and runs `env -i <the spec's environment> <argv>` in the spec's folder, so the program gets exactly that environment; `env` finds `pi` on the spec's `PATH`.

- **How it ends.** The VM is closed when the program exits, at the timeout, when the runner stops (the `signal`), and when the run writes too much ([What a run may take](#what-a-run-may-take)), and in every case before `run` returns. Closing the VM is what stops the program: aborting Gondolin's call doesn't. A run ended by a limit has `code: null`, even when the program ended at the same moment.
- **A VM that doesn't boot in time**, by its start limit or by the run's own time, makes `run` reject; what the runner makes of that is in [Failures](run.md#failures). *Why a limit of its own:* Gondolin's default is 2 minutes, which a VM that never starts would spend at every try. A VM boots in about 2 seconds with KVM and 6 under emulation, so `VM_START_TIMEOUT` leaves room for a loaded machine and a VM inside a VM.
- **A run ends when the program has exited and its output has closed**, not when it exits: a process the program leaves running with its stdout or stderr open holds the run until that process ends, or until the timeout, which then fails the run as timed out. pi's tools run the programs they start with pipes of pi's own, by a reading of pi's code, so what a tool leaves running doesn't hold pi's output.
- **The log:** `sandbox.vm_closed` says how the VM ended, in `ended`: `timeout`, `stopped` or `writes` when the sandbox ended it; `exited` when the program did; `lost` when Gondolin's call failed under the program, as when its QEMU was killed, which is also logged as `sandbox.vm_lost` with the error's name and code (`errorFields`), not its message, which can quote the guest's output; and `not_started` when it never booted. A lost VM's run has `code: null`, and the runner records it as "pi was stopped".
- **Nothing carries over between runs.** Each run is a new VM from the same image: pi's home, `/tmp`, anything it installed and any process it left running are gone when the VM closes. Only what it wrote where it may write survives.
- **Size:** `VM_MEMORY_BYTES` and `VM_CPUS`, which milestone 0's checks of pi ran with, images included. pi, its tools and the files it reads run in the memory, and so do the VM's `/tmp` and `/root`.

## What a run sees and may change

The runner asks, for every run (`piFiles`), for the data folder as `root`, mounted at its own path, so the paths in the prompt and in pi's tool calls read the same everywhere; of it, for what the agent's `reads` and `writes` name, and `run/`, to be seen; for the run's `writes`, the agent's own or a backfill's narrower ones ([Backfill](rebuild-and-backfill.md#backfill)), and `run/session/`, to be changed; and for the agent's `sessions/` to be hidden ([agents.yaml](configuration.md#agentsyaml)). Whatever `reads` and `writes` say, `run/` is read-only but for `run/session/`, so pi can't change the index file, `show`, the zone rules or any copy there, and `sessions/` isn't there: `agents.yaml` can't put either in `writes`. With the default `reads` and `writes`, the VM sees the datastore and the agent's folder, and may change `views/`, `memory/` and `run/session/`.

Nothing else of the host is visible: the folders that lead to what the VM sees hold only what leads there, and only a folder leads there: a file on the way to an entry, which a change of `writes` can leave ([A change of writes](run.md#a-change-of-writes)), isn't shown. So with the default configuration pi can't change the datastore, the outbox, the locks, `state.json`, the git history, another session or the config folder, and can't read another session.

The sandbox mounts `root` through three providers, outermost first, the first two `view.mjs`'s (`viewProvider`), and the third `gondolin.mjs`'s (`budgetedProvider`):

1. **What may change** (`WritesProvider`), which refuses with `EROFS` every operation that changes something, unless `writes` lets the run do it at that path, as Gondolin's `ReadonlyProvider` refuses them all. The operations are those Gondolin's file system service calls: `open` for writing, which is also how a file is made and how `truncate` reaches one; `mkdir`, `rmdir`, `unlink`, `rename`, from and to, `link`, the file linked to and the new name, `symlink`, `chmod` and `truncate`. Writes, `fallocate` and `copy_file_range` go through a file opened for writing, so they need nothing more. A folder of `writes` lets everything happen in it, and to itself only `mkdir`, `rmdir` and `chmod`, so the run can make it when it isn't there and can't put a file, a link or another folder in its place, or move it; a file of `writes` lets the run do anything to that one path but make or remove a folder there, or move one there, and nothing to a folder that is there in its place. Nothing is done through a link whose last name leads nowhere: the host would make what it names, wherever that is. The VM's kernel never asks that, since it follows a link itself; and Gondolin's `RealFSProvider` refuses it as well, with `ENOENT` ([Facts about Gondolin 0.14.0](#facts-about-gondolin-0140)).
2. **What may be seen** (`ViewShadow`), Gondolin's `ShadowProvider` with a `link` of its own, which it lacks: a path that is hidden, or that is in no entry of `reads` or `writes` and leads to none, isn't there. Reading it fails with `ENOENT`, listings leave it out, and a link on the host that leads to it is taken for it. A listing is judged in the folder the host lists, too: given straight to the service, a link is listed as the folder it leads to, which then shows only what that folder shows. And `lstat`, `readlink`, `unlink` and `rename`, which act on a link itself, judge it by its own name, where `ShadowProvider` judges what it leads to.
3. **What a run may take** ([What a run may take](#what-a-run-may-take)), over Gondolin's `RealFSProvider` of `root`.

- **Each operation is judged twice:** at the path the VM gave, normalized, and where the host would act, through the links on the host the operation would follow, all of them for `open`, `chmod`, `truncate` and the file `link` links to, and those on the way to the last name for the rest. Both must be allowed. *Why:* pi runs as root in its VM and could talk to the file system service itself, not through the VM's kernel, which follows links on its own: with any name, `..` included, and with a path whose last name is a link that pi made where it may write. `RealFSProvider` follows a link on the host to anywhere inside `root`, and `root` is the whole data folder: a link of pi's in `views/`, opened for writing that way, would otherwise write `state.json`. `test/view.test.mjs` calls the provider so.
- **Links in the VM.** The VM's kernel follows a link itself, inside its own file system, so a link made where the run may write leads only to what the VM sees, and a write through it is judged at the path it leads to. A link made in a writable folder that names `sessions/`, from beside it or by its full path, ends at a path that isn't there, and a hard link to a hidden file fails too. The link itself is there, and the run can list it, move it and remove it, as any of its own.
- **`sessions/` is hidden.** *Why:* the agent's folder, read-only, would show pi every earlier session. The owner chose this on 2026-11-16, asked whether pi may read `sessions/`: "hide it from the VM with Gondolin's `ShadowProvider`, in milestone 7. pi does not see `sessions/`." Only `sessions/` is hidden: `state.json` and `.git` stay readable and can't be changed, and pi can read history with `git log`.
- **Gondolin's own mount point** is moved (`vfs.fuseMount`) to `/run/gondolin-vfs`, a temporary file system Gondolin's boot sets up. *Why:* Gondolin 0.14.0 puts its file system at `/data` in the VM by default, which is where the data folder is in Docker, and shows the mount there a second time, through the same providers. With the data folder at `/data` and its mount point there, the VM doesn't start.
- **A refused change** comes back to pi as an error, `EROFS: read-only file system`, and the run goes on. `touch` on a file succeeds in the VM and changes nothing on the host. Gondolin's service has no `chown`, `utimes` or `mknod`, so the VM can make no FIFO or device anywhere: `mkfifo` fails with "Not supported".
- **One mount, not one for each entry.** *Why:* `writes` names files as well as folders, and a file can't be mounted on its own; a mount of the folder it is in would show the VM all that folder holds, and a mount inside another would hide from it what the outer one shows. *Cost:* host links resolve within the whole data folder rather than within each folder, which is why each change is judged where the host would act, and each read through a link at the path it leads to.

## Environment

pi's environment is only `PATH`, `HOME` (`/root`, a fresh folder inside the VM), `LANG=C.UTF-8`, `TZ=<SCOOTER_TZ>`, `ICU_TIMEZONE_FILES_DIR=<the run's icu-tz/>`, `PI_SKIP_VERSION_CHECK=1`, `PI_OFFLINE=1`, `PI_TELEMETRY=0`, and `OPENROUTER_API_KEY` set to the run's placeholder (`piEnv`, with the placeholder from the policy). The real key never enters the VM ([The key](network-policy.md#the-key)).

- *`PATH`* is the run's `bin/`, then the folders of the image, `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`. So `env` finds `pi` in the image, and pi, and the programs its tools start, find `show` by its name in the run's copy ([show, and the runner's skill](agent.md#show-and-the-runners-skill)), first, whatever the image holds. `bin/` is in `run/`, which the VM can't change. A `PATH` has no way to quote a `:`, so the runner refuses a `DATA_DIR` that holds one ([The env files](configuration.md#the-env-files)).

- *Why `env -i`:* a program run in a Gondolin VM also gets the variables the VM's boot sets, `PATH`, `HOME`, `TMPDIR`, `TERM`, `PWD`, `SHLVL` and five that point programs at Gondolin's certificate authority, and variables passed with the call are added to those. Through `env -i` it gets exactly the variables given. pi works with that list and nothing more: Alpine's Node trusts the system's certificates, to which the VM's boot adds Gondolin's authority. The boot's `PATH` leaves out `/usr/local/bin`, where pi is.
- *Why `TZ`:* Scooter's own code never depends on its process's zone ([Time](shared-code.md#time)), and only pi gets the owner's, because it writes what the owner reads. Two readers in the VM take the zone from it, each with rules of its own: the image's C library, and so the programs pi runs, such as `date`, with the image's zone files, its `tzdata` ([The VM image](#the-vm-image)); and the VM's Node, `show` and pi, with ICU's zone rules that `ICU_TIMEZONE_FILES_DIR` names. The image's zone files are of the release Alpine's `tzdata` had when the image was built, and the zone rules of the release that ships with the runner, so for a zone whose rules changed between the two, `date` and `show` can give two times.
- *`ICU_TIMEZONE_FILES_DIR`* is the run's copy of ICU's zone rules that ship with the runner, `run/icu-tz/`, read-only as the rest of `run/` ([The zone rules](agent.md#the-zone-rules)). ICU reads its zone files from that folder in place of those built into Node, so the VM's Node converts times with the runner's rules, whatever the image's Node has built in, tz 2024b in the test image, which put some zones an hour off. pi gives the programs its tools start its own environment, the variable with it, so `show` gets it from pi's `bash` tool too (`VM 7`, and the sandbox's test of the agent's instructions). The image doesn't change for it: it holds the Node Alpine's release has, and `config/image/build.json` stays as it is.
- The arguments of a program arrive in the VM byte for byte, in the folder given, and no shell reads them; a missing folder and a missing program both end with exit code 127.

## Acceleration

- **`auto`**, the default, uses the fastest accelerator available: KVM when the runner can open `/dev/kvm` for reading and writing and it is a character device, otherwise emulation, which it logs as `sandbox.emulation` with the reason; the runner logs which at its start, `scooter status` shows it, and falling back to emulation also sends the owner one notice ([status.json](runner.md#statusjson)).
- **`kvm` or `emulation`** is taken as it is. A forced accelerator that can't be used stops the runner, with an error that says how to enable it, natively and in Docker, and points at `doctor`, rather than quietly using another. *Why:* Gondolin falls back to emulation silently, which is about ten times slower, and asked for KVM explicitly (`accel: "kvm"`) it fails instead.
- **`hvf`**, Apple's hypervisor, is a known value kept for macOS ([Deferred and out of scope](../ARCHITECTURE.md#deferred-and-out-of-scope)); on Linux it can't be used, so it stops the runner like any other forced accelerator that isn't there.
- Gondolin is always told which (`accel`), so it never chooses by itself. *Why opening the device:* that is what QEMU does; an ACL, or Ubuntu's device rules, which reset per-user ACLs, can let a permission check pass where the open fails. *Not covered:* a device that opens where the hypervisor itself doesn't work, as in a VM without nested virtualization; then every VM fails to start, runs pause as setup errors, and the log says why.

## The machine

QEMU's `q35` machine on x86_64, with KVM as under emulation (`machineType`); on arm64 Gondolin's own `virt`. *Why:* Gondolin 0.14.0 gives x86_64 `microvm` with KVM, which hangs in the guest kernel's APIC setup under nested KVM with 2 processors, as in a VM of a cloud provider, where `q35` boots; on the machine itself `q35` boots sooner too, 1.0 to 1.35 seconds against 1.8 to 2.2 for `microvm`. *Cost:* `q35` has firmware and a PCI bus that `microvm` hasn't, so QEMU needs SeaBIOS and iPXE's ROMs, which Debian's `qemu-system-x86` and Ubuntu's QEMU bring.

## What a run may take

Nothing pi does may stop the runner, or keep the bridge from writing.

- **Output:** the sandbox keeps the first `SANDBOX_STDOUT_MAX_BYTES` of pi's stdout, its answer, and the last `SANDBOX_STDERR_MAX_BYTES` of its stderr, where OpenRouter's error is, as they arrive, and says `stdoutCut` (`createOutput`), which fails the run ([Failures](run.md#failures)). *Why that much:* with `-p` pi prints its answer alone, a few kilobytes; `ANSWER_MAX_TEXTS` texts at their longest are under 1.4 MB, and an answer near the limit is already one the runner wouldn't send whole.
- **Writes:** the mount counts, for the run, the bytes written and the names made, files, folders, symbolic and hard links, against `RUN_WRITE_MAX_BYTES` and `RUN_NAMES_MAX_COUNT`, beneath the providers that judge them, so only what the run may change is counted. The write or name that passes either is refused with `ENOSPC`, as is everything after, and the VM is closed; the result says `wroteTooMuch`, which fails the run, and the clean-up then frees what it wrote ([Failures](run.md#failures), [The clean-up](run.md#the-clean-up)). *How:* Gondolin 0.14.0 has no quota, but every write, open, folder and hard link made through a provider passes its file system hooks; a symbolic link passes them by, so the sandbox counts it itself. *Why bytes written and names made:* they bound the blocks and the inodes a run can take, whatever it removes again; counting the space a file takes would let a run rewrite a file without end. The limits leave room for what a run may leave several times over. *Cost:* a run that rewrites a large view many times could reach the limit; the hooks see writes in pieces of at most 60 KB, so what passes the limit is at most that much.
- **The VM's own disk** is a copy-on-write overlay that can't grow past the image's size, and its `/tmp` and `/root` are in its memory, so the rest of what a VM writes isn't on the host's disk.

## Supervision

If the runner dies, its VMs must die with it. Gondolin 0.14.0 leaves a VM's QEMU running, cut off from the network, when the process that started it is killed alone; killed with its group, QEMU goes too, since Gondolin starts QEMU in the group of the process that started it. So the runner always runs under something that stops its whole process group, as its systemd unit and its container do ([The units](install.md#the-units), [The image](install.md#the-image)). Run by hand in development, nothing guarantees it. Either way the disk overlay, the sockets and the VM's place in Gondolin's list stay behind, in the runner's temporary folder, which the next start empties.

## The runner's own folders

Gondolin keeps its certificate authority and its session files in the home folder of the user it runs as, and its disk overlays and sockets in the temporary folder. So when the sandbox opens, it sets, in the runner's own environment, `HOME` to `runner/home`, `TMPDIR` to `runner/tmp`, `XDG_CACHE_HOME` to `runner/home/.cache` and `GONDOLIN_SESSIONS_DIR` to `runner/tmp/sessions`, then loads Gondolin.

- The certificate authority stays in `home/`, given to each VM as `mitmCertDir`, so it lasts from one start to the next.
- Gondolin's list of running VMs, with a socket for each, goes in `tmp/sessions/`, where a socket's path is shortest.
- `tmp/` is emptied at every open, before any VM, because a runner that was killed leaves files there.
- The sandbox refuses to open when a socket's path there would pass 107 bytes, the most a Unix socket's path takes, and says the data folder needs a shorter path. Gondolin puts five sockets in the temporary folder, with names of up to 37 bytes.

*Why the runner sets them:* it then works the same however it was started, as a service, by hand or in a container, and the folder it empties is the one Gondolin uses. Gondolin fixes the folder of its list of running VMs when its module loads, so the module loads only after; under `home/.cache/gondolin/sessions` a socket's path passed 107 bytes with a data folder of 33 bytes. The runner's programs get environments of their own ([Running programs](shared-code.md#running-programs)), so they see none of these.

## The boot check

`bootCheck`, which `doctor` uses ([doctor](install.md#doctor)), boots one VM from the image as a run does, with the sandbox's own checks and the accelerator the runner would use, runs `true` in it, and reports the accelerator and how long the boot took. Its home, temporary folder and network log are a folder of its own in the system's temporary folder, or in `/tmp` when the owner's `TMPDIR` is too long a path for Gondolin's sockets there (`socketsFit`), removed afterwards: nothing in the data folder changes, and a runner at work keeps its own folders. The VM sees an empty folder of it, may change nothing, and reaches no host. Its `signal` closes the VM, so a `doctor` stopped during the boot leaves no QEMU. *Why `/tmp`:* a boot that failed only because the owner's `TMPDIR` made the sockets' paths too long had `doctor` give a misleading fix; `/tmp` avoids that folder, rather than a message that names it.

## The VM image

pi's VMs boot from an image Scooter builds with Gondolin's image builder: Alpine Linux, at the release `build.json` pins, with:
- Node.js ≥ 22.19, and pi at its pinned version;
- `pdftotext` and `pdftoppm` (poppler), `heif-convert` (libheif) and git, for the agent's files;
- ripgrep and fd, which pi would otherwise download from GitHub while it runs;
- `tzdata`, so the image's C library, and the programs pi runs, know the zone in pi's `TZ`: without the zone files, Alpine's C library falls back to UTC and says nothing. The image's Node doesn't read them: its ICU has zone rules built in, tz 2024b in the test image, and in the VM it converts with those that ship with the runner instead ([Environment](#environment)); and `curl`, which the protocol tells the agent to use when internet access is on ([The protocol](agent.md#the-protocol));
- `git config --system --add safe.directory '*'`, so pi can read the mounted repository's history: without it git refuses the repository as being of "dubious ownership", since its files are the runner's user's and the VM runs as root. `git log` and `git status` then work on the read-only folder, and `git commit` fails, changing nothing.

Alpine's base brings busybox's `sort`, `awk` and `sed` too. Every program the agent's instructions name is in the image, and a sandbox test looks for each in a VM with `command -v`.

**The build file**, `config/image/build.json`, says what is in the image, not how it is built: it names no architecture and no container build, which `build-image` chooses, so it isn't a complete Gondolin config, and `gondolin build --config` doesn't take it as it is. Its packages are those above, `npm`, which installs pi, and Gondolin's own default list: `linux-virt`, `rng-tools`, `bash`, `ca-certificates`, `ca-certificates-bundle`, `e2fsprogs` and `e2fsprogs-extra`. Its build commands are three, in this order: `npm install --global --ignore-scripts --omit=dev --no-audit --no-fund @earendil-works/pi-coding-agent@1.5.2`, `npm cache clean --force`, and `git config --system --add safe.directory '*'`; none of them runs pi or anything else npm installed. In the image, pi's version is in pi's `package.json`, `/usr/local/lib/node_modules/@earendil-works/pi-coding-agent/package.json`.
- *Alpine 3.23.8:* 3.23 is the branch Gondolin 0.14.0 builds from by default, and packages come from the branch's current index whatever the pin says, so its newest fix release is the one whose base matches them. It was still the newest on 2026-11-18. Alpine's packages float within a release, which is why `packages.txt` records them.
- *pi 1.5.2* stays pinned: the network policy's allowlists are its requests ([What pi sends](network-policy.md#what-pi-sends)).

**pi's pin, read strictly.** The build file's commands must name `@earendil-works/pi-coding-agent` exactly once, counting every mention with or without a version, a path among them, and that once as `@earendil-works/pi-coding-agent@<x.y.z>`, an exact version, in a command that is `npm install`, pi's package with its version, and switches from a short list, `--global`, `-g`, `--ignore-scripts`, `--omit=dev`, `--no-audit` and `--no-fund`, `--ignore-scripts` among them, and no other word: plain words of letters, digits and `@/._=:+,-`, apart by spaces, so the shell reads it as that one command. The build file must not name `arch` or `container`. Otherwise `build-image` and the runner refuse, naming the command. *Why:* a range or `latest` would let two builds hold different pis under one pin, and a command without `--ignore-scripts`, or with a word npm reads as turning the scripts back on, such as `--ignore-scripts false`, `--no-ignore-s` or `--ignore-s=false`, would run pi's packages' code as root in a native build: npm 10.9.8 takes a word after a switch as its value, and a switch by the start of its name. The build file is the owner's, so this guards against a slip, not an attacker: the other commands are still the owner's to choose.

**`scooter-image.json`.** Beside Gondolin's files, it holds `builtAt` (the build time Gondolin's `manifest.json` records, to the second), `pi` (from pi's `package.json` in the image), `alpine`, `arch`, and `zones`, every file under the image's `/usr/share/zoneinfo`. `packages.txt` lists the installed versions, and says which index it used and when: the base system's packages are those `/lib/apk/db/installed` records in the image, and the others are resolved, right after the build, against the APKINDEX of each repository the image's `/etc/apk/repositories` lists, the way Gondolin 0.14.0's builder resolves them: the first repository that lists a name wins, names are also found through what packages provide, dependencies are followed with their version constraints dropped, and a conflict (`!name`) is taken as a dependency; a version so resolved replaces the base system's. Each index is fetched within `APK_INDEX_TIMEOUT`, its body included, or the build fails. *Why:* Gondolin's builder unpacks Alpine's packages without recording them, so `apk info` in the image lists only Alpine's base, and no other source records the versions. *Cost:* the index is fetched again about a second after the build fetched it, and Alpine updates it a few times a week, so a package updated in between would be listed at its new version, and the native build keeps Gondolin's index for up to a day in root's cache, which could make that gap longer; the resolution reimplements Gondolin's, which an upgrade of Gondolin must be checked against.

**The check at a start.** When it opens, before anything of Gondolin runs, the sandbox reads the build file's pin and refuses, with a `SandboxSetupError`, when the image is missing, isn't whole, has no `scooter-image.json`, holds another pi, was built for another architecture, or doesn't know `SCOOTER_TZ`, written as the tz database writes it, case and all, by the image's own zone files, which is what pi's C library looks up; so `Asia/KOLKATA` stops the runner. Each error says what to do, and stops the runner ([Starting up](runner.md#starting-up)). `scooter status` shows when the image was built. *Why `scooter-image.json`:* it is written at build time, so the runner needs neither `debugfs` nor a VM to check it.

## build-image

`scooter build-image` builds the image into `runner/image/`, from the build file in the config folder.

- **How.** As root, Gondolin's native build; otherwise its container build with Docker, else Podman; otherwise it stops, saying it needs root, or Docker or Podman. In the runner's container in Docker it says to use the `build-image` container instead, `docker compose run --rm build-image`, with exit code 2: neither the runner's user nor its read-only container can build there ([The build-image container](install.md#the-build-image-container)). The build file goes to Gondolin as it is, with the machine's architecture and the method added.
- **One at a time.** It holds `runner/runner.sock` while it builds, as [One service per data folder](shared-code.md#one-service-per-data-folder) says, and its refusal says to stop the runner first. *Why:* a running runner must not boot an image it didn't check at its start.
- **Beside the runner's folder.** It builds into `.image-build/image/` in the data folder, beside `runner/` and so on the same file system, made 0700 by the user who builds; reads the image there, with `debugfs`, from e2fsprogs, out of `rootfs.ext4`, so no mount, no root and nothing in the image runs, `debugfs` being looked for in `/usr/sbin` and `/sbin` too; records it; checks that the pi in it is the pinned one; and gives it to `scooter-runner` when root. Then, in `runner/`, it makes two renames and nothing else: whatever is at `runner/image`, a link included, out to `.image-build/old`, and the new image in. Anything in the new image's way that a rename can't replace fails the build, with the new image left in `.image-build/` for the next build to remove. The old image is removed in `.image-build/` as a handed-over folder is: a link or a file in its place is unlinked, and a folder has each of its names unlinked and is then removed, which happens only once that empties it. That empties an image because Gondolin's image is a flat folder, with no folder in it; an image that held one would be left at every build. What can't be removed is logged as `image.old_left`, and stays where only root reaches it, and the next build refuses, saying to look at it. Leftovers of a build cut short are removed at the next.
- **As root** it refuses a data folder that isn't root's or that another user can write, a `.image-build` that isn't a folder of root's, and a missing `runner/`, rather than make the runner's folder as root; `setup` makes it. Without root, in development and for the container build, it builds the same way, with no other user to guard against.
- *Why outside `runner/`:* `scooter-runner` owns `runner/` and could put a link anywhere in it at any moment; a build in `runner/` had root write into the folder a link led to, give it and every name in it to the runner's user, and set its mode, so that an escape from pi's VM could reach the bridge's secrets ([Why it is built this way](../ARCHITECTURE.md#why-it-is-built-this-way)). A rename follows no link at either end, and puts a folder only where nothing or an empty folder is; binding the socket and removing it reach only that name. A check before each step would leave the gap that [Folders other users control](../ARCHITECTURE.md#folders-other-users-control) accepts for the bridge; building where the runner's user can't reach leaves it no step to turn. A process of the runner's user that was inside the old image can still change what it holds after the rename, though no path leads it there any more, and nobody but root can rename it.
- **Exit codes:** 2 for a fault in how it is set up or called: the build file, no method, no `debugfs`, a runner running, a folder it may not write, which for a user who isn't root on a native install, `scooter-runner` among them, says it runs as root there; 1 for a build that fails.
- **What a native build runs as root:** Gondolin's builder runs the build's commands in a chroot, which needs root, with the host's `/proc` and `/dev` mounted in it, and a chroot doesn't contain root. So the build runs as little as it can there: Gondolin's builder, then Alpine's shell, npm and git inside the image's folder. Gondolin unpacks Alpine's packages itself and runs none of their scripts; pi is installed with `--ignore-scripts`, and the build's commands never run pi or anything else npm installed, so no code from pi's packages runs as root on the host; and the build runs only when the owner starts it, never in a service. The owner confirmed this on 2026-11-15, on the condition that if pi turns out not to work without its install scripts, the owner decides again: pi 1.5.2 does, with all seven of its tools ([Facts about pi 1.5.2](agent.md#facts-about-pi-152)); if a later pi doesn't, stop and ask the owner. *Cost:* a native build runs as root on the host, where an unprivileged user was meant. What the build costs in Docker, in a privileged container of its own, is in [The build-image container](install.md#the-build-image-container).
- It needs `cpio`, `lz4` and `e2fsprogs`, and QEMU's `qemu-img`. A build takes about 16 seconds, and the image is about 530 MB.

## Facts about Gondolin 0.14.0

Checked on Ubuntu 24.04 with QEMU 8.2.2. The rest of what the network policy relies on is in [Facts about Gondolin's network](network-policy.md#facts-about-gondolins-network).

- **What it is:** micro-VMs run by QEMU or krun, with their network and file mounts controlled from Node. It needs Node ≥ 22.19, and `qemu-img` as well as `qemu-system-x86_64`, and works when installed with `--ignore-scripts`.
- **Backends:** QEMU with KVM works. krun crashed at boot ("Kernel doesn't fit in RAM") with every image and memory size tried, so QEMU is used. Without usable KVM, Gondolin quietly falls back to emulation; asked for KVM explicitly it fails instead.
- **Timings**, for a pi run whose model replies came back at once:

  | | QEMU + KVM | Emulation | Emulation, in a rootless container |
  |---|---|---|---|
  | VM boot | 1.8–1.9 s | 6.1–6.4 s | 4.3–4.4 s |
  | VM start to pi's first request | 2.5–2.7 s | 13.7–14.0 s | 12.7–13.1 s |
  | A whole 6-turn pi run | 2.9–3.0 s | 16.5–16.7 s | 15.9–16.1 s |
  | `pi --version` in the VM | 0.47 s | 5.8 s | — |
- **Starting:** `VM.create()` begins the boot and returns before the VM has booted, and `start()` waits for it; with `autoStart: false`, `start()` fails at once with "sandbox is stopped".
- **Closing** a VM while pi runs returns at once, 36 ms with KVM; Gondolin's call is rejected, with "server is shutting down", QEMU is gone, and the temporary folder and Gondolin's list of running VMs are emptied; what pi wrote in the writable folders stays, such as the session file it had begun in `run/session/`. Killing a VM's QEMU while a program runs makes Gondolin's call reject at once, with a plain `Error`, which has no code.
- **Files:** the folder of Gondolin's list of running VMs is fixed when its module loads: `GONDOLIN_SESSIONS_DIR`, or else `gondolin/sessions` under `XDG_CACHE_HOME` or `~/.cache`. The certificate authority's folder is looked up when a VM is made, and `sandbox.mitmCertDir` sets it. Gondolin keeps both under `~/.cache/gondolin` by default, and its disk overlays and sockets in the temporary folder, which it looks up at each VM.
- **Mounts:** the data folder, mounted through the providers of [What a run sees and may change](#what-a-run-sees-and-may-change), worked for pi's reads and writes, `run/session/` two levels down inside the read-only `run/` among them, and the host sees what the run writes at once. A guest's write reaches the host in pieces of at most 60 KB (`MAX_RPC_DATA`), and `copy_file_range` and `fallocate` go through the same writes, or make holes. A symbolic link made through a provider passes the file system hooks by (`SandboxVfsProvider.symlink`); writes, opens, folders and hard links pass them. `ShadowProvider` has no `link`, so a hard link through one fails with `ENOSYS` unless the provider over it gives one, as `ViewShadow` does.
- **What the file system service asks of a provider**, by a reading of Gondolin's `FsRpcService`: `lookup`, `getattr`, `readlink`, `readdir`, `open`, `read`, `write`, `create`, `mkdir`, `symlink`, `unlink`, `rmdir`, `rename`, `link`, `access`, `truncate`, `chmod`, `fallocate`, `copy_file_range`, `release` and `statfs`, one at a time, each with a path it joins from a folder's and a name, and normalizes. `create` is `open` with a flag that makes the file; `truncate` opens the file `r+` when the provider has no `truncate` of its own, as Gondolin's mount router hasn't; `write`, `fallocate` and `copy_file_range` act on a file already opened. `RealFSProvider` follows links on the host for `open`, `stat`, `readdir`, `mkdir`, `chmod`, `symlink`, `access`, `realpath` and the file `link` links to, refusing one that leads outside its root, and a last name that is a link leading nowhere, as `ENOENT` (`test/view.test.mjs`); and only those on the way to the last name for `unlink`, `rmdir`, `rename` and the new name of `link`. Of a file it opened, the service asks only `read`, `write`, `truncate`, `stat` and `close`, never `writeFile` or another call that acts by the file's path: `RealFileHandle.writeFile` writes by the path, whatever the file was opened for, so a file opened for reading writes nothing only because the service never calls it.
- **What the VM sees of it**, tried in a VM (`VM 6` in `test/tools/vm.test.mjs`): each change outside what `writes` names, `open` for writing, appending and making, `mkdir`, `rmdir`, `unlink`, `rename` from and to, `link` from and to, `symlink`, `chmod` and `truncate`, fails with "Read-only file system", leaves the host as it was, and the VM goes on; a program gets `EROFS`; each is allowed inside a folder of `writes`; a file of `writes` that isn't there can be made, and a name beside it can't; a write through a link the VM made, to what it may not change, fails the same way; a link it made to what it doesn't see can be listed, moved and removed, and what it leads to isn't there; `mkfifo` and `mknod` fail with "Not supported" anywhere.
- **In the VM**, `/root`, `/tmp` and `/var/tmp` are temporary file systems made at boot, `/root` and `/tmp` each up to half the VM's memory, and the root disk is ext4 with about 96 to 99 MB free.
- **Images:** the builder unpacks Alpine's packages itself, without recording them, and runs none of their scripts. It runs the build's own commands in a chroot, with the host's `/proc` and `/dev` mounted inside, and refuses to do so unless it is root. Its container mode runs the whole build as root in a privileged container instead, which under rootless Docker needs no root on the host. The image's `manifest.json` holds the build config, pi's install command included, and the build time. The image also holds Gondolin's own programs for the VM, such as `sandboxd` and `sandboxfs`, so a new Gondolin needs a new image, though the build file stays as it was.
- **Versions:** Gondolin is pre-1.0. Its documentation describes a newer, unreleased design in which a separate program runs the hooks; 0.14.0 runs everything in Node. *Cost:* upgrading it means porting the policy and running its tests again ([the network policy](network-policy.md)).

The checks of milestone 0, which show these, are tests in `test/tools/vm.test.mjs`, run with what the runner asks a run to see and change (`designFiles` in `test/support/vm.mjs`, which is `piFiles`), through the sandbox's own providers, so that they show what the sandbox relies on. One also shows the agent's folder without the hiding, to show what the hiding is for.

`test/support/vm.mjs` makes Gondolin's cache folder, `scooter-vm-*`, in the real temporary folder when the module loads, in every process that imports it, whether or not a VM test runs, and removes it when the process exits. *Why:* Gondolin fixes the folder of its list of running VMs when its module loads, as above, before any test has a folder of its own. *Cost:* a process that is killed leaves the folder behind; and it is one folder for each test process, where each test otherwise works in its own.
