# A run, and the agent's folder

A run is one run of pi, in one VM, on one batch or scheduled task, from the lock to the state: the executor of [the runner](runner.md), `performRun`, which the runner calls when its planner says to run. This document covers the run, what the runner reads and accepts of what pi left, what it does after a failure, and the agent's folder, which the runner makes, owns, and is the only committer of. A job's batches, of `scooter backfill`, are runs too ([backfill](backfill.md)).

## Files

- `src/runner/run.mjs`: one run: the lock, the sandbox's spec, then what follows a success or a failure.
- `src/runner/report.mjs`: reading what `send` and `mark` left, and the messages and reactions it makes.
- `src/runner/failures.mjs`: the cause of a failure, pauses, attempts, the state after a run, and the notices.
- `src/runner/agentdir.mjs`: the agent's folder, `run/` before each run, with the index file and a copy of the zone rules, the session copied back, and what the run could write in `run/` cleared.
- `src/runner/git.mjs`: git, run on the agent's repository; the file check, the commit and the clean-up.

## A run

1. **The lock.** The runner takes `run.lock`, and gives way to a backup, as [The locks](exchange.md#the-locks) says (`acquireRunLock`).
2. **`run/`.** `prepareRun` removes `run/` with `removeTree` ([Files another program controls](shared-code.md#files-another-program-controls)), however deep what pi left there goes, and makes it again: `config/`, the run's copy of the prompt and the skills, each at its path in the config folder, so `skills/expenses` is `run/config/skills/expenses`, a file that can be run keeping that, and `prompts/lifelog.md` what pi appends to its system prompt ([How pi is run](agent.md#how-pi-is-run)); `skills/scooter/`, the runner's own skill, and `bin/show`, `bin/send` and `bin/mark`, programs pi finds on its `PATH` ([show, and the runner's skill](agent.md#show-and-the-runners-skill), [send and mark](agent.md#send-and-mark)); `icu-tz/`, ICU's zone rules, which every Node in the VM converts times with ([The zone rules](agent.md#the-zone-rules)); `index.txt`, the index file ([The index file](#the-index-file)); `session/`, with the session's copy ([The session's copy](#the-sessions-copy)); and `send/`, empty, where `send` queues messages. `marks.txt`, where `mark` writes, isn't there until `mark` makes it ([What send and mark leave](#what-send-and-mark-leave)). A backfill's run copies only its skills, beside the runner's. All of `run/` but `session/`, `send/` and `marks.txt` is read-only in the VM, and the runner reads none of that back: only the session ([The session's copy](#the-sessions-copy)), and what `send` and `mark` left. A link in a skill's folder isn't copied: `prepareRun` refuses it, since a copy that followed it would show pi whatever it leads to. *Why a copy:* pi sees only that run's copy, never the config folder itself, which belongs to the owner.
3. **pi.** The runner gives the sandbox the run's spec: pi's command line ([How pi is run](agent.md#how-pi-is-run)), the agent's folder as its working folder, what the VM sees and may change and the environment ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change), [Environment](sandbox.md#environment)), `timeout_minutes`, and the network policy for the agent's model and the internet setting ([the network policy](network-policy.md)) (`runSpec`). What a run may change is the agent's `writes`, or a job's narrower ones, and `run/session/`, `run/send/` and `run/marks.txt`: the sandbox refuses every other change, so nothing after the run compares what changed with what might.
4. **After it:** [After a successful run](#after-a-successful-run), or [Failures](#failures).
5. **The lock** is let go of, after the packing ([After a successful run](#after-a-successful-run)) and the clean-up, which have no time limit.

## The session's copy

- **Sessions belong to the runner.** They are kept in `sessions/`, as `sessions/<session ID>.jsonl`, which the agent's own runs never see ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)). Before a run, `run/session/` holds only a copy of the current session, if there is one, under that name, and only if it is a regular file.
- **After a successful run**, once the files are committed, `keepSession` takes from `run/session/` the newest file pi named itself, `…_<session ID>.jsonl`, or else the copy, which pi continued, and copies it to `sessions/<session ID>.jsonl` with `copyUntrustedFile` ([Files another program controls](shared-code.md#files-another-program-controls)), up to `SESSION_MAX_BYTES`. It reads the folder as a stream, so millions of names cost time, not memory. Anything else in the folder is ignored. Any error is a refusal: a file it can't open, such as one pi made unreadable, a name that isn't UTF-8, a link, a socket, a folder it can't list, a full disk. A refusal is logged as `runner.session_refused`, with the error's code; the run still counts as a success, and the session kept before stays.
- **After a failed run** nothing is copied back.
- **Either way**, `run/session/` is emptied before the run is recorded, after a failed run before the clean-up, since pi could have filled the disk there, and so are `run/send/` and `run/marks.txt`, after a run that passed once they are read (`clearRunWrites`). Each folder stays, so emptying it makes nothing. An error in emptying one is logged as `runner.run_left`, naming it, and the next run's `prepareRun` removes `run/` whole ([A run](#a-run)). A start clears the three the same way, before it makes any folder ([Starting up](runner.md#starting-up)).

So a run can only extend the session it continues: it can't change another session, or plant one for a later day. *Why after the commit:* a session kept before the commit would remember a run that a failed commit, or a crash between the two, then threw away. Kept after it, a crash between the two leaves the files committed and the session without the run, so the next try sees the rows it filed.

*Facts about pi 1.5.2's sessions*, which this relies on, checked in a VM: pi writes one file into the session folder and nothing else, `<UTC time>_<session ID>.jsonl`, such as `2026-11-16T00-03-41-509Z_lifelog-2026-11-09.jsonl`, whose first line names the session and the working folder. A second run with the same ID prints nothing, sends the earlier conversation again, and appends to the same file. pi finds a session again by that first line, not by the file's name, so a copy under another name is continued; the working folder is part of the match, so after a restore to another data folder the day's session starts afresh, in a second file with the same ID, and the runner takes the file pi wrote, not the one it copied in. A new ID prints a warning on stderr, "Warning: No project session found…", which nothing reads. The system prompt and the skills aren't taken from the session: a continued session is sent with those of the current run, so the agent's prompt and the skills are current on every run of a day's session. pi sends the session's ID to OpenRouter in an `x-session-id` header.

## The index file

Before each run `prepareRun` writes `run/index.txt` from the runner's index of the datastore, as far as the runner had read it when the run began (`indexFileText`): one line for each `seq`, in order, with where the line is, its day's log and its line number there, its kind, and the `seq` of the line it points at, if any. `show` reads it in the VM, and the agent can search it ([show, and the runner's skill](agent.md#show-and-the-runners-skill)):

```text
1051 /data/datastore/2026/11/09/log.jsonl:213 message
1053 /data/datastore/2026/11/09/log.jsonl:215 message 1043
1054 /data/datastore/2026/11/09/log.jsonl:216 edit 1051
```

- **A line points at** its `target`, an edit's, a deletion's or a reaction's, or else at what a message replies to, its `replyTo`. Only a line this version's store didn't write can have both, and then it points at its `target`. A line of a kind or a channel this version doesn't know is in the file with its kind as the line has it ([Reading a line](datastore.md#reading-a-line)).
- **The paths are the host's,** which the VM sees at the same paths ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)). The reading check holds a kind to a name and a `seq` to a whole number, so a line of the file is read back one way, from both ends, whatever the data folder's path holds between them; and the runner refuses a `DATA_DIR` that holds a line break, which would split a line of the file ([The env files](configuration.md#the-env-files)).
- **A line written after** the runner last read the datastore isn't in it, so `show` doesn't show it during the run.
- **It is read-only in the VM**, as all of `run/` but the run's own places is, and the runner never reads it back: the next run's `prepareRun` makes it anew.

*Cost:* a line of the file for each line of the datastore, written before every run. For 100 lines a day over five years, 182,500 lines, it was 10 MB with the data folder at `/data` and 12 MB at `/var/lib/scooter`, written in 0.26 to 0.41 seconds on the machine Scooter was built on; `show` reads only the lines it needs of it, in 0.08 seconds there for a line near its end. It is in backups, as all of `run/` is.

## What send and mark leave

Once a run has passed, and only then, the runner reads what `send` and `mark` left in `run/` ([send and mark](agent.md#send-and-mark)), and acts on it ([After a successful run](#after-a-successful-run)): what a run that failed queued goes nowhere, and what it marked settles nothing ([Failures](#failures)). Nothing in pi's output decides anything or reaches a log: pi's last message isn't read, and the sandbox keeps its stdout only for the tests ([What a run may take](sandbox.md#what-a-run-may-take)). *Why held until then:* a failed run sends nothing, so a retry can't ask the same question twice, and a line settles only once what the run filed is committed.

```text
run/send/1.json   {"text":"Is this ticket for you alone, or for Sam too?","replyTo":1052}
run/send/2.json   {"text":"Filed the coffee and the lunch."}
run/marks.txt     done 1050
                  done 1051
                  failed 1053 the PDF needs a password
```

pi wrote both, as root in its VM, so they are read as files another program controls, and nothing in them may stop the runner, hold it up, or make it give the same lines again without counting an attempt: anything that isn't what `send` or `mark` writes is passed over, counted and logged, never thrown (`report.mjs`).

**The marks**, `run/marks.txt` (`readMarks`):
- The file is read with `readUntrustedFile` ([Files another program controls](shared-code.md#files-another-program-controls)): without following a link, without waiting for a writer, only if it is a regular file with one name, and of at most `MARKS_MAX_BYTES`. Otherwise it is refused whole, and logged as `runner.marks_refused` with the error's code: a link, a FIFO, a folder or a file with two names (`EUNTRUSTED`), one too large (`EFBIG`), one the runner can't read (`EACCES`). No marks count then, so every line of the batch is given again, with its attempt counted. No file is no marks. *Why refused whole:* a part read could drop a later `failed` of a line marked `done` before it.
- Each line is `done <seq>` or `failed <seq> <reason>`, a `seq` written as the index file writes it, a whole number from 1 of at most 15 digits. Any other line, half a line at the end, which `mark` never leaves, a number of twenty digits or with a leading zero among them, is counted and passed over, and logged as `runner.marks_unreadable` with the count.
- A line marked done is finished. One marked failed is given up on, into `failed`, and not tried again; its reason is the first one given, cut to one line of `REASON_MAX_CHARS`, or "no reason given". One marked both ways is failed: the agent said it couldn't handle it. One marked neither way is given again, up to `MAX_ATTEMPTS` ([Failures](#failures)). The agent tells the owner why a line failed with `send`, so the runner sends no notice.
- A line marked that the run wasn't given is ignored and logged as `runner.marks_unknown`, with how many and the lowest `LOGGED_SEQS_MAX` of them. A scheduled run is given no lines, so all its marks are. Only a line's own mark settles it: the runner settles no line because of another's mark, or of a message about it. A message already deleted, which no run is given, is the one the runner settles itself ([The batch](runner.md#the-batch)).

**The messages to send**, `run/send/` (`readSends`):
- The folder is read as a stream, without following a link to it, so a million names cost time and no memory: at most one name is held for each message that can go out. A name `send` doesn't give, anything but `<n>.json` with n a whole number from 1 of at most 15 digits, without a leading zero, a name that isn't UTF-8 among them, is counted as refused. Of the entries left, the first `RUN_MAX_SENDS` by their numbers are read, and those after them are dropped unread, and counted. A folder that can't be read, or isn't one, gives no messages, and is logged as `runner.sends_unreadable`.
- Each of those is read with `readUntrustedFile`, up to `SEND_ENTRY_MAX_BYTES`, and must hold what `send` writes: a JSON object of `text`, a string that isn't blank, and `replyTo`, when given, a `seq`, and nothing else. One that doesn't, a link, a FIFO, a folder, a file with two names or one the runner can't read among them, is refused, and its place isn't taken by one after it. A text is made well formed: half of a pair of UTF-16 surrogates, which a JSON escape can give and no channel can send, becomes U+FFFD. A text past `TEXT_MAX_CHARS`, or one holding U+0000, is made one that can be sent as any entry's is ([Outbox entries](exchange.md#outbox-entries)).
- What was dropped is logged once, as `runner.sends_dropped`: `past`, the entries after the first `RUN_MAX_SENDS`; `refused`, what wasn't what `send` writes; and `silent`, the messages of a run that sends nothing. *Why the limit:* a misled run can't flood the owner's chat: 2,000 messages would take nearly 3 hours of sending, one every `SEND_INTERVAL` ([Pacing](delivery.md#pacing)).

**The outbox entries** (`sendEntries`, `ackEntries`), written as [After a successful run](#after-a-successful-run) orders them:
- Each message is a text of the agent's. With a `replyTo` that names a message, the owner's or one Scooter sent, it replies to it, quoted; one that names an edit or a deletion replies to the message it changes. One that names a reaction, or a number that is no line, and a message without `replyTo`, is `about` the batch's newest item, so that it follows the owner's latest message ([Outbox entries](exchange.md#outbox-entries)); a scheduled run's has no `about`, so it goes to `DEFAULT_CHANNEL` ([Choosing the channel](delivery.md#choosing-the-channel)).
- In quiet mode, with an `ack_reaction`, the runner also writes a `react` entry for each line marked done that is a message, still there, and that no message of the run replies to: those got a reply instead. Reacting to a message the owner has deleted would say nothing. A message whose reply was dropped, past the limit or refused, gets its reaction.
- Each of the agent's entries, texts and reactions alike, carries the channels its `sends` names, and the bridge drops one whose channel isn't among them ([Choosing the channel](delivery.md#choosing-the-channel)). With `sends: []` nothing the agent says is written to the outbox.
- A job's runs send nothing: what they queued is dropped, and they get no reactions ([Its batches](backfill.md#its-batches)).

## After a successful run

pi runs as root in its VM, and what it writes where it may write is the runner's on the host, so pi chooses every name, mode and size there, how deep the folders go and how many files there are. The runner checks, commits and cleans up what the agent's `writes` names in its folder, the agent's repository ([The agent's folder](#the-agents-folder)), and never reads a path of `writes` outside it. Nothing it leaves may stop the runner, at the end of the run or at the next start, or make it run the same batch again without counting an attempt. So what the runner accepts is limited before git reads anything; what git doesn't record is put back once the check has passed; an error in checking or committing fails the run; and the clean-up can't be slowed down or stopped by what pi left.

A run passes when pi exits with 0 and its files pass the check below. Then, in this order, with no step between pi's exit and the commit that looks at what pi wrote beyond the check: the owner decided to drop the validation function, which issue 25 notes could be added there later.

1. **The check.** If what the repository keeps holds anything git wouldn't record, the run fails ([Failures](#failures)), with the reason `unexpected file <path>`. An entry with a nested `.git`, or a folder the runner can't read, on its way is the exception: git doesn't look into it, the run passes, and nothing of the entry is committed ([A change of writes](#a-change-of-writes)). Its entries are walked in their order, a folder's names in name order, by the bytes of the names, which reaches a name that isn't UTF-8 as it is on disk, without following links; an entry that isn't there is passed over, and so is one whose way is blocked ([A change of writes](#a-change-of-writes)), and one that is a file is a name like any other. The first of these is the unexpected file:
   - an entry in the other shape than `writes` gives it: a file or anything else where it names a folder, or a folder where it names a file. The VM can make neither ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)), and only a change of `writes` leaves one, which the clean-up then leaves out ([A change of writes](#a-change-of-writes));
   - a name that starts with `.`, such as `.gitignore` or a nested `.git`;
   - anything that isn't a regular file or a folder, such as a link or a FIFO;
   - a file the runner can't read, or a folder it can't read and search: pi can take the runner's access away from what it writes. Root reads every file, so a runner run as root, as in some tests, passes such a file and commits it;
   - a file with more than one name, a hard link, which git would commit as two files, and a later write through one name would change the other;
   - a path longer than the system takes: `mkdir` in the VM stops at the host's limit, but moving a folder into another doesn't;
   - the name at which the files and folders of the entries pass `AGENT_FILES_MAX_COUNT` together, each folder read as a stream and only that far, the name being the one in the order the folder gives them;
   - the file at which their sizes, as the file system gives them, pass `AGENT_FILES_MAX_BYTES` together.

   Then `git status --ignored=matching` names any file git ignores. Last comes staging, `git add -A --ignore-errors -- <entries>`, so a path git refuses, such as `git~1`, or a file it couldn't read, is left unstaged and named. A file of `writes` that isn't there and isn't in the last commit isn't given to git, which would refuse it; one that is in the last commit is, and its removal staged. An entry whose way is blocked isn't given to git, whatever the last commit holds. With no entry, git is given nothing, since given no path it would take the whole tree. Every path is taken as it is written, never as a pattern (`GIT_LITERAL_PATHSPECS`): the owner writes them ([Facts about git, Node and Linux](#facts-about-git-node-and-linux)). Staging is part of the check because only git knows every name it refuses. The path is logged cut to `REASON_MAX_CHARS`: it is a name pi chose, which could hold a message's words.
   *Why the limits:* git reads every byte of a file to add it, holes included, and pi can make a file of any size in an instant, all holes; some of git's work, such as taking names out of its index again, grows faster than their number, and pi can make hundreds of thousands of names in a run ([Facts about git, Node and Linux](#facts-about-git-node-and-linux)). They are on all the entries together, so that many small files can't add up to the same wait. Within the path limit a tree is at most about 2,000 folders deep, which the walk and git handle. *Cost:* a last commit past either limit, which only a commit by hand or a lower limit could make with the default skills, fails every run until it is smaller.
   *Why ordinary runs pass:* pi 1.5.2's `edit` and `write` leave nothing beside the files they change, no temporary files, dotfiles or locks.
2. **What git doesn't record, put back,** just before staging, once the rest of the check has passed:
   - **the modes:** every folder 0700, and every file 0600, or 0700 when its owner may run it, which is all git keeps of a mode, setting only a mode that differs. *Why:* a folder left without write access, or a file left read-only, made every later run fail to write there, and nothing in git said why. A mode that keeps the runner from reading still fails the run: the check has to read what it checks. The files' times aren't put back: no later run depends on them;
   - **the empty folders,** removed, the deepest first, so a folder that held only empty folders goes too, and after the modes, so a folder pi left without write access can't hold one back. A folder of `writes` itself stays, and is made again if pi removed it. They don't fail the run: an ordinary run can leave one, such as a folder once the only file a skill kept in it is gone.

   So after a successful run what the repository keeps holds nothing the commit doesn't, with the runner's modes, and nothing hidden carries over to later runs.
3. **The commit,** only if what was staged differs from the last commit: `lifelog: #1050 #1051 #1053`, every item of the batch, or `lifelog: scheduled task 21:30`, as `Scooter <scooter@localhost>`, unsigned. A job's are in [Its batches](backfill.md#its-batches).
4. **The session,** copied back ([The session's copy](#the-sessions-copy)). Before it, what `send` and `mark` left is read, and cleared at once, and after it `run/session/` is emptied, so nothing pi wrote in `run/` takes room the session's copy, the outbox or the state needs ([What send and mark leave](#what-send-and-mark-leave)).
5. **The outbox,** from what `send` left: the messages, in order, then the notice of lines given up on, if any ([Notices](#notices)).
6. **The state,** from the marks: lines marked done leave `retry`; lines marked failed go to `failed`; lines marked neither way have used the attempt this run was ([Failures](#failures)); the cursor moves to what the batch covered; and `lastRun` is recorded.
7. **The ✅,** in quiet mode, for each message marked done that no message of the run replies to ([What send and mark leave](#what-send-and-mark-leave)).
8. **Packing.** After a run that committed, once the state is saved, the runner runs `git gc --auto` itself, in the foreground, while it still holds `run.lock`, with no time limit; it packs only what is loose, and, once there are 50 packs, all of them again. A failure is logged as `agent.pack_failed`, and changes nothing else. *Why:* `git commit` would otherwise start `git gc --auto` in the background once enough objects are loose, outside `run.lock`, where a backup could read `.git` while packs are written and loose objects removed, and a start could no longer take it that no git of the runner's is running. Turning packing off would leave every version of a view a whole object; packing inside the commit would let a slow pack fail a run that had committed. Stopped part-way, git would leave `repack` and `pack-objects` writing on their own, since only the program itself is signalled ([Running programs](shared-code.md#running-programs)). *Cost:* the next round of the loop waits for it. Packing and the clean-up's removal have no time limit and `run.lock` has one; a backup past that time still waits while the runner holds its socket ([The locks](exchange.md#the-locks)).

*Why this order:* issue 25's, and a crash up to the state only means the batch runs again. The agent then sees the rows it already filed, so it doesn't file them twice; and the session never remembers rows a crash threw away. *Cost:* a crash between the outbox and the state gives the lines again with what the run sent already written, and the agent may then send a second time what it sent, a question among them. The prompt shows it nothing of what was sent ([The prompt](runner.md#the-prompt)). The day's session, kept before the outbox, holds the run that sent it, and the datastore, which the agent reads with `show`, the messages the bridge has sent and stored by then; with `session: none`, only the datastore does, and only once they have gone. A crash between the state and the ✅ loses the run's reactions: its lines are done, and the owner gets no ✅ for them. *Why the ✅ after the state:* a ✅ says a line is done, so it goes out once the state says so; written before, a crash would leave a ✅ on a line given again, which the agent could then mark failed.

**Errors.** Everything from the walk to the commit reads what pi left. An error there, such as a call of git stopped at `GIT_CALL_TIMEOUT`, fails the run as pi's own failure, with the reason `couldn't commit the run's files (<error>)`, counts an attempt, and is logged as `runner.files_failed`. *Why:* stopping the runner instead would run pi on the same batch again at every start, without counting one. *Cost:* a git that fails for a reason of its own, such as a damaged repository or a full disk, uses the items' attempts, and the owner is told.

## Failures

A run fails when pi exits with a code other than 0, times out, is stopped, or its VM is lost; when it wrote more than a run may ([What a run may take](sandbox.md#what-a-run-may-take)); and when it leaves an unexpected file, or files that couldn't be checked or committed ([After a successful run](#after-a-successful-run)). What pi printed counts for nothing. Then the runner clears what the run could write in `run/`, unread: `run/session/`, and what `send` and `mark` left, so nothing it asked to send goes out and its marks count for nothing, also when it marked before it failed or timed out. Then it runs [the clean-up](#the-clean-up), and works out the cause:

- **What pi left comes first:** an unexpected file after a run that exited with 0, an error in checking or committing, or a run that wrote too much, is pi's own failure, whatever the network log says; a run that wrote too much was closed in the middle of whatever pi was doing.
- **Otherwise the cause comes from OpenRouter's last answer during the run,** in the runner's own network log ([The log](network-policy.md#the-log)): from the run's start to its end, the last `request` to `openrouter.ai`, or the last request the policy refused there, whichever came later, and what came of it:
  - **a setup error:** a `response` of 401, 402, 403 or 404, such as a revoked key, no credit left, a model the key's guardrail doesn't allow, a model that's gone, or no endpoint meeting ZDR;
  - **an outage:** a `response` of 408, 429 or a 5xx, an `error` line, or nothing at all, because the run ended while it waited;
  - **pi's own:** another status, or no request at all.
  - **A refusal by the policy:** before any request had gone out to OpenRouter in the run, a setup error, "the network policy refused pi's request: <reason>"; after one had, pi's own failure, "the network policy refused a request: <reason>". *Why:* nothing the agent does can run before the model's first answer, so a refusal before one is pi's own request, and the policy and the pinned pi disagree, which no try of the batch can mend; pausing holds the messages without using their attempts. A later refusal may come from a program the agent ran, and reading it as a setup error would hold runs back for as long as the message that misled it is in the batch. *Cost:* a pi whose later requests differ in shape from its first, which pi 1.5.2's don't, would use the items' attempts.
  - A request the agent makes itself, with the placeholder, in the shape of pi's, is read the same way: nothing tells it from pi's own. The owner accepted this; what it costs is among the README's [Known limits](../../README.md#known-limits).
  - A log that can't be read counts as no answer from OpenRouter, so the run is pi's own failure, and is logged as `runner.netlog_unreadable`.

  The window can't take in another run's lines, because runs are at least `POLL_INTERVAL` apart ([The loop](runner.md#the-loop)).
- **A sandbox that can't run pi at all,** such as a VM that doesn't boot in time, also within the run's own time, is a setup error, "the VM couldn't start": it is the machine's fault, and spending every message's attempts on it wouldn't help.

**The short reason** is OpenRouter's error whenever its last answer was a status of 400 or more, whatever the cause, a 400 or a 413 for a prompt or an image too large among them: OpenRouter's own words when the last line pi printed on stderr is its error for the same status ([Facts about pi 1.5.2](agent.md#facts-about-pi-152)), as `OpenRouter: No endpoints found matching your data policy`, and otherwise `OpenRouter answered 429`. Without an error from OpenRouter it is `OpenRouter didn't answer`, `timed out`, `pi exited with code 3`, `pi was stopped`, `pi wrote more than a run may`, or `unexpected file views/.gitignore`. OpenRouter's words go into the notice and the state, cut to `REASON_MAX_CHARS`, and never into Scooter's logs, which carry the cause and the status.

**What each cause does:**
- **Setup error:** no item counts an attempt. Runs pause: nothing starts until the next try, every `SETUP_RETRY_WAIT` and at every start, until a run gets through.
- **Outage:** no item counts an attempt, and the runner tries again after the waits of `OUTAGE_RETRY_WAITS`, by the number of tries, the last repeating.
- **pi's own:** every item of the batch counts one attempt, its reason "not marked" for an item a run that passed didn't mark, or the failure's short reason, and is due again `RETRY_WAIT` later. *Why so soon:* these failures come from the model or the message, not from outside, and the model often succeeds on another try. After `MAX_ATTEMPTS` an item goes to `failed` with "not handled after 4 attempts", and the owner is told. `failed` keeps the newest `FAILED_KEEP`, in the order they were added.

**Pauses.** A try that fails for the same cause continues the pause: one try more, `since` kept, and the wait that goes with it. Another cause starts a new pause. Any run that gets through ends it: a success, or a failure of pi's own, which means OpenRouter was answering. A paused batch's items wait in `retry`, due at once, their attempts unchanged, so they come first in the next try's batch, and messages that arrived meanwhile join in: the whole batch is handled once OpenRouter works again, and nothing a setup error or an outage holds up ends in `failed`. A start brings the next try forward, after the quiet period. A task that fails this way stays due. A job's batch pauses every run as a live run does, but for a job of an agent given in a file, which has a model of its own: its setup errors and outages leave the pause as it is, and make that job wait on its own, in its file, with the same waits, which a start doesn't bring forward ([Its batches](backfill.md#its-batches)).

**The cursor** moves to what the batch covered after every run that finishes, failed or not, and the items it didn't handle wait in `retry`, which comes first in the next batch. Only a run cut short, by a crash or a stop, leaves the cursor and the state as they were. *Why:* the planner takes every work item after the cursor as new, so an item waiting in `retry` after the cursor would be given again at once, as attempt 1.

## Notices

Notices are outbox entries `by: "runner"`, which go to `DEFAULT_CHANNEL` ([Choosing the channel](delivery.md#choosing-the-channel)), and carry no channels: they go out whatever the agent's `sends` says, also with `sends: []`, which is about what the agent sends. So a failure's notice that names an unexpected file, a name the run chose, reaches the owner whatever `sends` says, cut to `REASON_MAX_CHARS`, as it did before `sends`.

- **The first failure in a row** sends one notice; later failures send nothing until a run succeeds: "⚠️ I couldn't process your last messages (<short reason>). I'll try again." A setup error's says instead "Runs are paused until this is fixed. I'll try again every 30 minutes." A task's names it by its trigger's `tag`, "run the scheduled task check-in", and says when it runs again. A task is a live run, so a failing task can be the first failure of a row, and one that gets through ends the row.
- **Items given up on:** one notice listing them: "⚠️ I gave up on #1051 ("coffee 120") and #1052 (a photo) after 4 attempts. Send them again if they matter." Each item is named by its text as it is now, cut to `NOTICE_QUOTE_CHARS`, or by what it holds; an email as `email "<subject>"`, the subject cut the same way. The subject is the email channel's, in the line's `data`, and is used only when it is a string there, else `""` ([data](datastore.md#data)).
- **A job that waits:** when a setup error or an outage starts the wait of a job of an agent given in a file, one notice that names the job, why, and that the owner's messages go on meanwhile; nothing more while the wait goes on ([Its batches](backfill.md#its-batches)). A job's other failures send none.
- **The emulation notice** ([status.json](runner.md#statusjson)) and **the restart notice** ([Restarts](runner.md#restarts)).

## The clean-up

After a failed run, and at every start, the runner throws away the run's uncommitted changes in what the repository keeps, the entries of the agent's `writes` in its folder, so the next try starts from the last good state. A path of `writes` outside the agent's folder keeps what a failed run left there ([agents.yaml](configuration.md#agentsyaml)). Nothing pi left can slow it down or stop it, and everything pi wrote is freed before anything new is made, since pi may have filled the disk, and on a full disk a new folder has no room. The exception is what a run the runner never cleaned up after left on the way to an entry under an earlier `writes`, some of which stops it at every start ([A change of writes](#a-change-of-writes)). `run/session/`, `run/send/` and `run/marks.txt` have been cleared just before ([The session's copy](#the-sessions-copy)). First the way to each entry is judged: an entry whose way is blocked is passed over by every step, as one that isn't there, and `agent.entry_blocked` is logged, naming it ([A change of writes](#a-change-of-writes)).

1. **Set aside.** Each entry that is there, a file or a folder, is renamed into `agents/.discarded/<agent>/`, under a number nothing there has, such as `1`, so that the name is never longer than the system takes, whatever the entry's is, after a folder is given write access, which a rename needs and pi could have taken away. A rename takes the same time whatever it holds, and no room. `agents/.discarded/` is beside the agent's folder, on the same file system, so nothing is copied, and outside what the VM sees and git. A start makes `agents/.discarded/<agent>/` and keeps it, so the clean-up makes nothing before it has freed what pi wrote.
2. **Removed.** Everything in `agents/.discarded/<agent>/` is removed with `emptyFolder` ([Files another program controls](shared-code.md#files-another-program-controls)), with whatever an earlier clean-up couldn't remove: without git, however deep it goes, reading each folder as a stream. If something can't be removed, the rest still is; `agent.discarded_left` is logged, and the next clean-up, or the next start, tries again. What is left is out of pi's sight and git's.
3. **Made again.** Each folder of the entries, empty, and the folder each file of them is in, so a file the agent may make has a folder to be made in. *Why here:* after what pi wrote is freed, a folder has room on a disk pi filled; pi may have removed an empty folder of `writes`, which the VM allows.
4. **Git's index** is the last commit's again: `git read-tree HEAD`, in one step, whatever the run staged.
5. **The files:** the last commit's files in the entries are written back, `git restore --source=HEAD --staged --worktree`, for each entry in the shape `writes` gives it: a folder's files for a folder, the file for a file. What the last commit has at an entry in the other shape is left out ([A change of writes](#a-change-of-writes)).
6. **The objects** nothing refers to, what `git add` copied into `.git/objects` for the run that failed, are removed: `git prune --expire=now`. A failure is logged as `agent.prune_failed`, changes nothing else, and the next clean-up tries again. *Why:* `git gc --auto` removes only what is two weeks old, so each failed attempt left what it staged, up to `AGENT_FILES_MAX_BYTES`, for good. It can remove them at once, not after two weeks, because only the runner uses the repository, and no git of its own runs then. *Cost:* every clean-up walks what the repository holds, milliseconds for years of views; objects someone staged by hand and left uncommitted go too.

Then the folders are checked, without the limits, since what the clean-up leaves is the last commit, which it can't make smaller. If anything is still there, or a step of git failed, the clean-up throws. After a failed run, the run is recorded first, with its attempt and its notice, and then the runner stops; at a start, the runner doesn't start; both say what is wrong. The clean-up comes before the run is recorded, so what pi left takes no room the state needs.

*Why the same way every time:* one way instead of two, and its only step that depends on what pi left is the removal, which needs neither git nor a time limit. *Cost:* each clean-up writes back every committed file of the entries, at most `AGENT_FILES_MAX_COUNT` and `AGENT_FILES_MAX_BYTES`; and `git read-tree HEAD` unstages anything staged outside them, which only someone working in the repository by hand would have staged.

These rules, and those of [After a successful run](#after-a-successful-run), answer the owner's choice, after reviews had found case after case of something pi leaves stopping the runner, to fix the whole kind of problem, by these four rules:
> - Limit what is accepted. Before git reads anything, check the number of files and their total size.
> - Put back what git doesn't record. Reset the permissions once the check has passed.
> - Fail the run, don't stop the runner. Any error that the agent's leftovers cause after it exits counts as a failed attempt.
> - Make the clean-up unstoppable. If it can't finish in time, set the folders aside and restore them from the last commit.

## The agent's folder

`agents/<agent>/`, owned by the runner's user, 0700, is a git repository:

| Path | Holds | In git |
|---|---|---|
| what `writes` names in it | with the default configuration, `views/`, with `expenses.csv`, `runs.csv`, `meals.csv`, `travel.csv` and `people.csv`, and `memory/`, with `preferences.md` and `needs-review.md` ([Memory](agent.md#memory)) | yes |
| `sessions/` | pi's sessions, hidden from the agent's own runs ([The session's copy](#the-sessions-copy)) | no |
| `run/` | made again before each run: `config/`, `skills/`, `bin/`, `icu-tz/`, `index.txt`, `session/` and `send/`, and `marks.txt` once `mark` makes it ([A run](#a-run)) | no |
| `state.json` | the runner's state ([State](runner.md#state)) | no |

**The repository keeps what the agent's `writes` names in its folder** (`agent.repository`): its entries, files or folders, in the order `writes` gives them, an entry in a folder another names left out, as that folder holds it. They are what the file check walks, what is committed, and what the clean-up puts back. *Why only those:* everything else in the folder is the runner's, or isn't the agent's to change. A path of `writes` outside the agent's folder is none of the repository's: the VM may change it, and the runner otherwise leaves it alone, as [agents.yaml](configuration.md#agentsyaml) says, with what that costs. The owner agreed to this, among the six points the plan of the agent model added to issue 25.

What pi can reach of it is in [What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change). Beside it, `agents/.discarded/<agent>/` holds what a clean-up sets aside, only until it has removed it ([The clean-up](#the-clean-up)).

### A change of writes

The owner can change `writes` so that what the last commit holds, or what a run under the earlier `writes` left, no longer fits it. Nothing of that stops the runner, at a start or at a run, but what the second's cost gives: some of what such a run left still stops it, fails its runs, or loses what the agent writes.

- **An entry in the other shape:** `memory` named as a file, with `memory/` committed as a folder, or the other way round. The VM could change neither: a folder of `writes` takes only `mkdir`, `rmdir` and `chmod` at its own path, and a file of `writes` nothing at a folder there. So the clean-up at the start sets it aside and doesn't write it back, a folder of `writes` is made, and the next run that passes commits its removal, with what that run wrote in the new shape. The check fails a run that finds one, which only a hand in the folder during the run could leave. *Cost:* what was committed in the old shape leaves the folder at the next start; it stays in git's history.
- **Something on the way to an entry:** a file, a link, or a folder the runner can't search, such as one of mode 000. `notes/2026/books.csv` named, under an earlier `writes` that named `notes/`, with `notes/2026` a file of the last commit; or with `notes/2026` a link, to anywhere, or such a folder, which a run under that `writes` made. The clean-up after that run would have set it aside with `notes/`, but a run the runner never cleaned up after leaves it: the runner killed while pi ran, or before the clean-up, by a `SIGKILL`, an out-of-memory kill or a power cut. So each name on the way, from the agent's folder down to the folder the entry is in, is judged by `lstat`, without following a link (`wayIsOpen`): a folder the runner can search, or nothing yet, and then nothing after it either. Anything else blocks the entry. It isn't the entry's, so the runner leaves it as it is: the clean-up, the check, staging and a job's `--empty` pass the entry over, as one that isn't there, before anything is set aside, made, staged, checked, emptied or read there, and each clean-up logs `agent.entry_blocked`, naming the entry. So the runner never acts where a link leads, outside every entry, and nothing it can't search stops it. Nor can the VM write through the way anywhere `writes` doesn't name: the sandbox judges where a link leads ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)). The owner removes what blocks the way to have the entry made at the next start. A file the last commit holds outside every entry isn't written back, and an entry the last commit holds isn't given to git while its way is blocked, so nothing of it is committed. *Why not refuse it at the start:* the check of `agents.yaml` reads nothing in the data folder, and a start that refused would refuse at every try until the owner found what blocks the way; passing over keeps the agent's other entries working, and the log names the entry. *Cost:* the way is judged only by what each name on it is. What else a run the runner never cleaned up after left there, under an earlier `writes` that named a folder it lies in, doesn't block the entry, and some of it stops the runner, fails its runs, or loses what the agent writes. The owner chose to leave two such cases as documented costs, the `.gitignore` below and a memory file the runner couldn't read, which stopped every run until the runner stopped reading the memory files ([Memory](agent.md#memory)), over fixing both in code. What the reviews tried, each with what the owner does:
  - **A folder on the way that the runner can search but not write**, such as one of mode 0500 or 0100, which such a run can leave too, doesn't block the entry: where the clean-up has something to set aside, make or write back in it, every start throws, with `EACCES` or with `git restore` failing, until the owner gives the folder its write access back, or removes it. The owner chose to leave it so, as a documented cost, over blocking such a folder as well or giving the runner its write access back.
  - **A `.gitignore` in a folder on the way.** git applies it to the entry below, though the folder is no entry's. Where it ignores the entry or a folder on its way, such as `*` in `notes/` for `notes/2026/books/`, or for a `notes/2026/books.csv` that isn't there, every start throws, `the clean-up left notes/2026/ in the agent's folder`. Where it ignores only the entry's file, such as `*.csv` for `notes/2026/books.csv`, the start works, and every run that writes the file fails, the check naming the file, with its attempt counted. The owner removes the `.gitignore`.
  - **A `.gitattributes` in a folder on the way**, such as `* working-tree-encoding=NOPE`. The start works, and every run that writes the entry fails, `couldn't commit the run's files (git add: exit code 128)`, with its attempt counted. The owner removes the `.gitattributes`.
  - **A nested `.git` in a folder on the way**, a folder holding `HEAD`, `objects/` and `refs/`. git takes the folder for another repository and doesn't look into it, so a run that writes the entry passes, and nothing of it is committed. Nothing stops, but what the agent wrote there stays outside git until a run fails, whose clean-up sets it aside, and it is lost. The owner removes the `.git`, and the next run that passes commits what is there.
  - **A folder on the way that the runner can search and write but not read**, such as one of mode 0300. As with a nested `.git`, git can't list it, and only warns: the run passes, nothing is committed, and a failed run's clean-up loses what the agent wrote. The owner gives the folder its read access back, and the next run that passes commits what is there.

- **Made at a start:** the folders, `git init`, a `.gitignore` listing `/sessions/`, `/run/` and `/state.json`, anchored with `/` so they can't match anything in what `writes` names, and a first commit, `lifelog: initial commit`, holding the `.gitignore` alone, on the branch `main`. Each step is safe to repeat, and a start finishes what a crash left: `git init` runs whenever there is no commit. The folders of `writes` are made by the clean-up that follows ([The clean-up](#the-clean-up)).
- **Git runs** from an argument list, on the agent's repository named outright (`GIT_DIR` and `GIT_WORK_TREE`), with an environment of its own: no system or user config, no hooks, no signing, `Scooter <scooter@localhost>` as author and committer, the time from the runner's clock, every path taken as it is written (`GIT_LITERAL_PATHSPECS=1`), and no maintenance started on its own (`maintenance.auto=false`, `gc.autoDetach=false` and `maintenance.autoDetach=false`). `GIT_CALL_TIMEOUT` bounds each call of git. *Why named outright:* without `GIT_DIR` git looks for a repository in the folders above, such as one holding the data folder.
- **Git's lock files.** A git killed while it holds the index or a branch, by a power cut or a `SIGKILL`, leaves `index.lock`, `HEAD.lock` or `refs/heads/main.lock` in `.git`, and git then refuses to add, restore, remove or commit until it is gone, so the runner couldn't start again. So with the agent's folder, at a start, the runner removes and logs every `*.lock` file at the top of `.git` and under `.git/refs/`, before it uses git. It holds `runner/runner.sock`, and no git of its own goes on in the background, so no git of its own can be running then; nothing else of Scooter's uses git there.
- **The runner is the only committer.** Git history is the audit trail for everything the agent changed, and the owner can see and revert it there.

## Facts about git, Node and Linux

Checked on the Linux machine, with git 2.43.0 and Node 22.23.2, and in a VM from the image; the check, staging, the commit and the clean-up rely on them, and so do `removeTree` and `emptyFolder` ([Files another program controls](shared-code.md#files-another-program-controls)).

- **git** `add` reads every byte of a file, holes included: 0.4 seconds for 100 MB of holes, 4.0 for 1 GB, 1.85 for 100 MB of random bytes, 32 for 8 GB of zeros; a file of holes past about 15 GB ran past `GIT_CALL_TIMEOUT`. `git add -A` of 300,000 empty files took 1.1 seconds, and of about 19,500 small files 0.1 seconds. `git rm -r --cached` of the names staged in a folder takes time that grows faster than their number: 7.6 seconds for 300,000, 52 to 57 for 800,000, and past `GIT_CALL_TIMEOUT`, at 63.6, for 900,000; `git read-tree HEAD` on the same index took 2 ms, and puts it back to the last commit whatever it held.
- **git** `add -A` exits with 128 and stages nothing for a file it can't read, and for a file or folder named `git~1` in any case, `core.protectNTFS` being on by default on Linux too; for a folder it can't read it only warns and passes over what is inside. With `--ignore-errors` it stages the rest, exits with 1, and leaves those paths unstaged, where `git status` names them. It adds a name that isn't UTF-8 as it is. `git status` doesn't see FIFOs, and says nothing of an empty folder, which `git add -A` doesn't record. `git add -A -- views memory` works on empty folders and fails on a missing one; `git restore` has no `--ignore-unmatch`, and fails on a path with no committed file.
- **git** `add -A`, given a path that is neither on disk nor in its index, exits with 128, "pathspec … did not match any files", and stages nothing; given one only in its index, it stages its removal. `git status`, `git diff --cached`, `git ls-files` and `git ls-tree` take such a path without a word. A path is a pattern, `views/?.csv` taking `views/b.csv`, unless `GIT_LITERAL_PATHSPECS=1`; and `git add -A` given no path takes the whole tree. Given a path whose kind changed since the index, a file become a folder or the other way, `git add -A` stages the removal of the one and the files of the other; a folder gone, the removal of its files. `git ls-tree -r` names a file by its path, and a folder by the files in it. A path that runs through a file, `git status`, `git diff --cached`, `git ls-files` and `git ls-tree` take without a word, and `git add -A` refuses with 128 one its index doesn't hold. `test/tools/git.test.mjs` holds these, with git 2.43.0.
- **git**'s leftover `index.lock` makes `git add`, `git restore`, `git rm` and `git commit` exit with 128, and a leftover `HEAD.lock` or `refs/heads/main.lock` makes `git commit` do so; `git status`, `git diff --cached` and `git ls-tree` work with any of them. `git rev-parse` on an empty `.git` exits with 128.
- **git** `commit` starts `git gc --auto` once about 6,700 objects are loose, counted by those in `.git/objects/17/`, and by default it goes on in the background after the commit has returned; with `maintenance.auto=false` it starts none, and `git gc --auto` with `gc.autoDetach=false` packs in the foreground, leaving no `gc.pid`.
- **Node** `readdir` gives a name that isn't UTF-8 with `�` in place of its bytes, a string that names nothing on disk (`ENOENT`); with `encoding: 'buffer'` it gives the bytes, which every `fs` call takes as a path. `fs.opendirSync` with `encoding: 'buffer'` reads a folder as a stream. `fs.rmSync` with `recursive` reads each folder whole into memory first, can't remove a folder whose mode is 000, and overflows the call stack on a tree about 1,980 folders deep, which a path within the limit can hold. Removing each name as it comes, while the folder is read, works on ext4 and on tmpfs: 900,000 files in about 7 seconds with 105 MB.
- **Linux** renames a folder into another folder only if the folder itself can be written, since its `..` changes: `EACCES` otherwise. Any call on a path longer than 4,095 bytes fails with `ENAMETOOLONG`, `lstat` and `access` included; in the VM `mkdir -p` stops there, but `mv` of a folder into one near the limit succeeds, and each move adds as much again. On ext4 a new folder needs a block of its own, so on a full disk `mkdir` fails with `ENOSPC`, while a rename into a folder that is there needs none.
- **A guest** makes about 1,360 files a second, so about 800,000 in a run of the default timeout, and `truncate -s 40G` in the VM took 9 ms.
