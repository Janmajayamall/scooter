# Rebuild and backfill

Both replay history through the agent, one of the owner's days at a time, without sending anything. A rebuild recreates what the agent's `writes` names in its folder, the views and the memory with the default configuration, and the sessions, from the whole datastore, with the runner stopped; a backfill fills one new view from the history before it was added, inside the runner, without stopping live work. Each replayed batch is a run as a live one is ([A run, and the agent's folder](run.md)), which sends nothing. What makes the views rebuildable is that the datastore is the only source of truth ([Why it is built this way](../ARCHITECTURE.md#why-it-is-built-this-way)).

## Files

- `src/runner/replay.mjs`: what a rebuild and a backfill share: a batch of one of the owner's days, `Now:` the batch's own time, a session for each day, and removing a replay's sessions.
- `src/runner/rebuild.mjs`: `scooter rebuild <agent>`: the tag, the reset, the replay, the one commit, and what it says on its output.
- `src/runner/backfill.mjs`: a backfill's batch, the prompt's line, its skills, its lane, and its summary.

## Replayed batches

Here and in backfills:

- **A batch is of one of the owner's days.** It is drawn as a live batch is ([The batch](runner.md#the-batch)): due retries first, then work items after its lane's cursor, at most `BATCH_MAX_ITEMS` and within `PROMPT_MAX_BYTES`, up to the `seq` the replay stops at. Every item it takes was sent on the local date, in `SCOOTER_TZ`, of the first item's `at`, and it stops at the first sent on another date. So a message caught up late, whose `at` is on an earlier day than those around it, is a batch of its own. A message that an edit or a deletion in the batch brings in, from the lane's retries or from what it gave up on, joins whatever its day, as it may take a batch past `BATCH_MAX_ITEMS`, and is shown with its date. *Why the local date, and not the session's day:* every item a batch takes was then sent "today" by its `Now:`; with the session's day, a message at 00:10 would share a batch with one at 23:50, and one of the two would be read against the other's date. *Cost:* a message sent just after midnight is in the next day's session, where a live run would have had it in the day before's until `SESSION_ROLLOVER_HOUR`; a session is the agent's conversation, not where anything is filed.
- **`Now:`** in the prompt is the time of the batch's newest item, the latest `at` among them, not the current time, so "today" and "yesterday" in old messages mean what they meant then, and `Now:` is never before an item it shows. Item times are shown against it, so the batch's items show only their time, and one brought in from another day its date too.
- **A message is shown as it is now,** as every message is ([The prompt](runner.md#the-prompt)): with its latest edit, even one sent on a later day, or as deleted. A rebuild reads the datastore once, when it starts, so for it "now" is then; a backfill's index is the runner's. *Why:* an index as of each batch's time would be a second one to keep, and the rebuilt views come out the same: the agent files the latest text, the later edit changes nothing when its batch comes, and a message deleted since is never filed. *Cost:* a replayed batch can show an edit or a deletion the owner made later than its `Now:`.
- **Sessions:** each of the owner's days gets its own, `<agent>-rebuild-<day>`, or `<agent>-backfill-<id>-<day>`; with `session: none`, none. A replay's sessions are removed when it is over: a rebuild's when it has finished, a backfill's when it finishes or a start drops it. Only names of the form `<prefix><date>.jsonl` go, so the backfill `people-1-2` keeps its own when `people-1`'s go. *Why:* they serve the replay alone, no live run uses them, and a rebuild of a year makes about 365, up to `SESSION_MAX_BYTES` each, in a folder that is backed up.
- **Locks:** each batch takes `run.lock` and gives way to `backup.lock`, as a live run does ([The locks](exchange.md#the-locks)), so a backup never sees half a batch.
- Rules the owner sent as messages are learned again at the point they were sent. Rules in the config folder apply to all of history.

## Rebuild

`scooter rebuild <agent>` runs as the runner's user, in Docker in a container of the runner's service, with the runner's service stopped; the README gives the CLI commands ([Rebuilds](../../README.md#rebuilds)). It takes one argument, the agent's name, reads `runner.env` as the runner does, since its batches need the key, opens the sandbox as the runner does, and readies the agent's folder as a start does, so uncommitted changes there are thrown away ([Starting up](runner.md#starting-up)). The bridge keeps running, so messages that arrive meanwhile are stored, and handled once the runner is back.

**Who else may run.** It holds `runner/runner.sock` while it runs, as [One service per data folder](shared-code.md#one-service-per-data-folder) says, and its refusal says to stop the runner first. *Why:* a runner's start would remove the rebuild's `run.lock` and git's lock files, and throw its uncommitted changes away. It also refuses while `run.lock` is there: holding the socket, it knows no runner is running, so such a lock was left by a runner or a rebuild stopped by force, and it says so, and to remove it. *Why keep that refusal:* removing the lock would be a second way to do what a runner's start does, for a case that needs a `SIGKILL`. *Cost:* after such a kill, the owner removes `run.lock` by hand, or starts and stops the runner, before a rebuild.

In order:
1. **The tag.** The current commit is tagged `before-rebuild-` and the start's UTC time to the second, written without `-` and `:`, which git refuses in a name: `before-rebuild-20261118T101500Z`. A name taken, which only two rebuilds in one second could make, fails the rebuild before it changes anything.
2. **Where it stops.** The newest `seq` in the datastore. Anything later is left for the runner, which handles it with replies.
3. **The reset.** What the repository keeps, the entries of `writes` in the agent's folder ([The agent's folder](run.md#the-agents-folder)), is emptied, a folder of its files and a file removed, and `sessions/` emptied, and that is committed, `lifelog: rebuild, from empty`, a path of `writes` outside the agent's folder left as it is; and `state.json` is reset, with `cursor` that `seq`, so a runner started after a rebuild cut short goes on from there. `backfillDone` holds the old list, the backfill in progress, which is dropped, and every `backfill` trigger of the config. *Why:* the rebuild covers their views; dropped without being counted done, the next start would run each again over the whole history, through a skill the rebuild already ran it through.
4. **The replay,** up to that `seq`, silently: nothing goes to the outbox, no notice either, and the rebuild says on its output what each batch did, why it paused and until when, and what it gave up on. It keeps its progress in memory, the live lane's fields of a state that is never saved, its cursor from 0, which `performRun` settles as it settles a live batch's. It handles failures in that lane as a live run's are handled ([Failures](run.md#failures)), but for two things: what it gives up on waits for the end (step 5), and what would pause runs holds the rebuild until the next try. While an item waits to be tried again, the rebuild waits until it is due, as for a pause, and takes nothing after it: the lane's cursor never passes the day of an item waiting. Each batch is committed as it succeeds, `lifelog: rebuild #1-#20`, the lowest and the highest `seq` of its items, so that a failed batch's clean-up ([The clean-up](run.md#the-clean-up)) comes back to the last good one. Before each batch it gives way to `backup.lock`, trying again every `POLL_INTERVAL`. A rebuild's batch has the prompt of a live batch, with `Now:` its own time, and no line of its own; the agent answers as for a live batch, and its texts and reactions go nowhere. *Why no line of its own:* the batch differs from a live one only in that `Now:` is in the past, while the VM's clock gives the real time, and the protocol already tells the agent that "today" is the date after `Now:` ([The protocol](agent.md#the-protocol)); the questions the agent asks again are followed, in the replay, by the owner's answers to the ones it asked the first time, which are in the datastore, so `memory/needs-review.md` comes out as a live run would have left it.
5. **The commit.** The branch is set back to the tagged commit with git's index and the files as they are (`git reset --soft`), and one commit is made, `lifelog: rebuild`, so its difference from the tag is what the rebuild changed. Then it packs the repository with `git gc --auto`, as a run that committed does ([After a successful run](run.md#after-a-successful-run)); a failure is logged as `agent.pack_failed`, and changes nothing else. The state is written again with what the rebuild gave up on in `failed`, the newest `FAILED_KEEP`, where an edit of the message brings it back into a live batch ([The batch](runner.md#the-batch)), and `lastRun` null, as a reset leaves it. The rebuild's sessions are removed.

Steps 1 to 3, and 5, take `run.lock` as a batch does, giving way to `backup.lock` and saying "Waiting for a backup to finish." once, so a backup never reads the agent's files or `.git` while the rebuild changes them, nor a branch naming a commit it hadn't read. Stopped while it waits before step 1, the rebuild has changed nothing, and says so. A runner's start takes no `run.lock` ([Starting up](runner.md#starting-up)).

*Why waiting out a setup error:* the owner can mend the key without losing what the rebuild had done. *Why the replay waits for an item tried again:* a rule the owner sent that needed a second try would otherwise be learned after the days that follow it were filed, and the retry's prompt would show what the agent had sent on later days. *Cost:* at most three minutes for each item not reported, and four attempts each. A backfill doesn't wait so: it files one view, its rules are the config's, and it runs inside the live runner, where it waits for nothing. *Why the batches' commits:* the clean-up needs a commit to come back to after each batch. *Cost:* the commits folded away stay in the repository until git's reflog lets them go, by default after 90 days. Packed, they take little; loose, each holds a whole compressed copy of every view its batch changed, and `git gc --auto` packs only once about 6,700 objects are loose ([Facts about git, Node and Linux](run.md#facts-about-git-node-and-linux)). Tried with the five default views at 20 rows a day, one batch a day: a year's rebuild left about 27 MB loose, 0.4 MB once packed; three years' left about 103 MB loose beside 0.9 MB of packs, 1.6 MB once all packed; a rebuild cut short leaves its commits on the branch, the next rebuild's tag among them.

**Stopping.** It stops on `SIGTERM`, `SIGINT` and `SIGHUP`, which a closed terminal sends: the batch in progress is thrown away, as at a runner's stop, and `run.lock` is let go of. Writing to a terminal that is gone fails, and the rebuild ignores that. Cut short, by a stop, a closed terminal or a crash, a rebuild leaves the agent's files rebuilt up to where it got, and says "with the agent's files rebuilt only in part", and is run again from the start. *Why not resumed:* keeping its progress on disk would need a field of the state that `scooter status` and the runner know, and a runner that refuses to start until the rebuild is finished. *Costs:* a rebuild run again spends again on OpenRouter what it had done; messages that wait when a rebuild starts get no reply, no question and no ✅, since they are replayed silently, and a rebuild run again after one cut short takes a new `seq`, so everything that arrived during the first try is filed so too; and a rebuild that didn't finish leaves no mark but the last commit's message, `lifelog: rebuild #…` where a finished one leaves `lifelog: rebuild`: after a crash or a reboot the runner's service starts again and goes on from `cursor`, with the views rebuilt in part, and neither its start nor `scooter status` says so, and a backup taken during a rebuild holds the same. The README says what to do about each ([Rebuilds](../../README.md#rebuilds)).

**Exit codes:** 0 once it has rebuilt; 2 for a call or a configuration it can't start with: no such agent, `agents.yaml`, a runner running, `run.lock`, a sandbox that can't run as it is set up; 1 when it fails or is stopped.

## Backfill

Live runs use a skill from the moment it's added, but the messages before that were filed without it. A backfill runs that history through the new skill alone, without touching the other views and without stopping live work: a rebuild for one view.

- **Starting one:** the owner adds the skill to the agent, then a `backfill` trigger for it, and restarts the runner ([Backfills](../../README.md#backfills)). At a start the runner starts the first `backfill` trigger whose ID isn't in `backfillDone`, with `until` the live cursor, its own cursor at 0, and empty lists. Live runs, which now load the new skill, handle everything after `until`, and the backfill everything up to it, so every message is covered once. Backfills run one at a time; the next starts at the next start. A backfill whose trigger left the config is dropped at the next start, without being counted done, and its sessions go.
- **When it runs:** a backfill batch starts only when nothing live is waiting: no work items after the live cursor, no due retries, and no scheduled task ([When the agent runs](runner.md#when-the-agent-runs)). Its work items are the live runs': lines of the channels the agent's triggers `on: new-messages` name, so an agent without such a trigger gives its backfill none. Runs still never overlap, so a new message waits at most for the backfill batch in progress.
- **Its own lane:** the backfill keeps its own `cursor`, `retry` and `skipped` in `state.json` ([State](runner.md#state)), and a batch's outcome does to them what it does to the live lane's (`settleLane`, [Failures](run.md#failures)), with `skipped` in the place of `failed`, from which an edit or a deletion in a later batch brings a message back as from `failed` ([The batch](runner.md#the-batch)). A setup error or an outage pauses every run, as after a live run, and a batch that gets through ends a pause. Its batches leave `lastRun` alone, which is the live runs', so a live failure after one is still the first of its row and sends its notice. Its progress survives a restart.
- **The batch:** work items after the backfill's cursor, up to `until`, with their context, replayed as [Replayed batches](#replayed-batches) has it. The prompt's first line, before the header every prompt has, names the backfill's skill and every path of its `writes`, as the VM has it: `Backfill (from your configuration, not a message from the owner): file these messages for the people skill only. Change only /data/agents/lifelog/views/people.csv and /data/agents/lifelog/views/people/.` pi gets the backfill's skill alone, and the system prompt of live runs, so the owner's current preferences apply to all of history.
- **What it may change:** what its `writes` names, which lies in the agent's own ([agents.yaml](configuration.md#agentsyaml)), and nothing else: the runner gives the sandbox its `writes` in place of the agent's for each of its batches, and the VM sees the agent's as it always does ([What a run sees and may change](sandbox.md#what-a-run-sees-and-may-change)). A write anywhere else, the agent's memory among them, fails in the VM with "Read-only file system", and the batch goes on. The check, the commit and the clean-up after a batch are a live run's: nothing compares what changed with what the backfill may change, which nothing but its `writes` could have.
- **Silent:** nothing is sent per batch. Texts, `REPLY_TO` and `NO_REPLY` are ignored, and failures send no notice. What the agent does with its guesses in a backfill is in [The protocol](agent.md#the-protocol).
- **Commits:** `lifelog: backfill people-1 #812-#831`, the lowest and the highest `seq` of the batch.
- **Finishing:** when the cursor reaches `until` and the backfill's retry list is empty, the runner sends one text, `by: "runner"`, to `DEFAULT_CHANNEL`, also with `sends: []`, as notices go ([Notices](run.md#notices)): `Backfill people-1 finished: views/people.csv has 143 rows, 12 marked ❓. Skipped: #1031, #1207.` It names each CSV file of `writes` in the agent's folder by its path from that folder, a folder's at any depth, in order; a write that isn't a CSV gives none; a CSV that isn't there says so; and a folder with none says so. A path of `writes` outside the agent's folder gives none: the runner never reads there. A row is what CSV reads as one after the header, blank ones left out, so a field in quotes may hold a line break; a row with ❓ anywhere in it is marked. Each file is read with the care of `readUntrustedFile`, up to `AGENT_FILES_MAX_BYTES`: it is what the last commit holds, but pi wrote it. Then the ID goes to `backfillDone`, and the backfill's sessions go. The text is written before the state is saved, so a crash between the two sends it twice and never loses it.

What `writes` may name, and the rest of a `backfill` trigger, is in [agents.yaml](configuration.md#agentsyaml).
